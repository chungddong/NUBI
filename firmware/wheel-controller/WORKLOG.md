## ~2026-08-08 (날짜 미상) · PC: 호버보드 링크 디버깅

> 날짜 근거: DEBUGGING.md, 첫 커밋 내용(세션 기록 없음) · 커밋: 2026-08-09의 두 커밋에 담김

DEBUGGING.md에 자세히 있고, 여기에는 포트폴리오 관점의 골자만 적는다.

- **결론**: 하드웨어 고장은 없었다. `DRIVING_MODE 0`(pwm)에서는 명령값이 곧 듀티라서 첫 테스트
  `s 30`(3 %)은 안 도는 게 정상이었다. 그 뒤 조사는 대부분 "측정 도구가 엉뚱한 장치를 보고
  있던" 문제였다.
- **프로토콜 식별**: 처음엔 EFeru FOC(115200, 0xABCD, XOR)로 가정했지만 캡처와 맞지 않았다. RoboDurden
  Gen2.x(19200, 22바이트 피드백, `'/'`로 시작하는 9바이트 명령, CRC16-XMODEM)로 정정했다. 다항식
  65536개를 브루트포스로 돌려 CRC를 확정했고, 나중에 업스트림 `CalcCRC()`와 같음을 확인했다.
- **핵심 교훈**: 펌웨어가 200 ms마다 찍는 리포트 줄은 보드가 꺼져 있어도 나온다. 그래서 "살아 있다"는
  근거는 실제로 디코딩된 프레임만 세는 `rx N` 카운터뿐이다. 잘못된 도구로 낸 결론 두 개가 유효한
  측정을 뒤집은 기록이 남아 있다.
- **진단 도구**: `d`(핀별 프레임 수, 패드 루프백 + 미연결 대조핀 GPIO25, 송신 프레임 hex, 풀업
  프로브), `y`(프레임 레이아웃 프로브), `r`(RC 시정수로 직렬 저항 추정), `k`(ShutOff로 명령 도달
  확인). 도구마다 "무엇을 증명하고 무엇을 못 보는지"를 표로 정리했다.
- **안전장치**: 클램프(부팅 시 400/1000), 램프(20/100 ms), 데드맨(텔레메트리 500 ms), 호스트
  워치독(opt-in `w 1`, GUI가 250 ms마다 `h`). 모든 타임아웃은 `loop()`의 단일 `iNow`와 비교해서
  unsigned 랩을 피한다.
- **STOP 부활 버그**: GUI 레이트리미터가 삼킨 값을 하트비트가 STOP 뒤에 흘려보내서 바퀴가 다시
  돌았다. `drop_pending` + `stopped` 래치 + 하트비트 억제로 고쳤다. 회귀 테스트 `test_stop.py`는
  양방향(고친 코드는 통과, 옛 코드는 실패)으로 단언하고, 벽시계 대신 시계를 주입한다.
- **도구**: `hoverctl.py`(tkinter 패널, 링크 품질 미터), `speedsweep.py`(듀티 스윕 → Kv),
  `speedcalc.py`(Kv → 속도/전류, 경사·다륜. 기본 Kv 14 rpm/V, 36.8 V), `ledtest.py`
- **4륜 계획 계산**: 20 % 경사에서 모터당 전류가 2륜 ~21 A → 4륜 ~8 A. 발열은 전류의 제곱으로 준다.

### 한 일 2: "왜 조향이 안 되는가": 업스트림 소스 분석

`Hoverboard-Firmware-Hack-Gen2.x-GD32/HoverBoardGigaDevice/Src/main.c`를 직접 읽고 pwm 모드
(`DRIVING_MODE 0`)의 믹싱을 수식으로 정리했다.

```
expo       = 1 − |speed| / 2000                  // 속도가 오를수록 조향을 절반까지 축소
steer'     = steer × expo
angle      = 90° − steer' × 0.09
x          = lookUpTableAngle[angle]              // 0°→ −1, 45°→ 0.3, 90°→ 1.0, x(90+k) = 1 / x(90−k)
outer      = speed
inner      = x × speed                            // 곱셈이라 speed = 0이면 조향도 0
STAND_STILL_THRESHOLD = 50                        // |명령| < 50은 0으로 처리
```

풀 조향(1000)일 때 안쪽 바퀴 듀티(업스트림 룩업 테이블로 계산):

| speed | 바깥 | 안쪽 |
| --- | --- | --- |
| 200 | 200 | −109 |
| 300 | 300 | **−120 (최대)** |
| 400 | 400 | −99 |
| 600 | 600 | −17 |
| 1000 | 1000 | +300 |

결론은 네 가지다.

1. 곱셈식이라서 제자리 회전 명령이 존재하지 않는다.
2. 안쪽 바퀴의 역회전 듀티는 최대 12 %인데 이 모터는 ~20 % 아래에서는 움직이지 못한다. 그래서
   안쪽 바퀴는 서서 끌리고, 바깥 바퀴는 200~300으로 기어가는 수준이 된다.
3. expo 때문에 고속에서는 조향 폭 자체가 줄어든다. 사람이 타는 호버보드에 맞춘 튜닝이다.
4. 부저는 `config.h`의 `#define BEEP_BACKWARDS` + `FlagStatus beepsBackwards = SET`으로 컴파일 때 정해진다.
   9바이트 명령 프레임에는 관련 필드가 없어서 ESP32에서 끌 수 없다. `speed < -50`인 쪽이 항상 울리므로
   장착 방향을 바꾸는 트릭도 통하지 않는다.

다음 날(09-18) Jetson 실측이 이 분석과 맞았다. `s +150`, `t +500`에서 마스터 바퀴는 1.11 → 0.24 km/h로
감속만 했다.

### 결정과 이유

| 선택지 | 내용 | 판단 |
| --- | --- | --- |
| 보드 믹싱 유지 | 지금 그대로 | 조향을 개선할 수 없음 |
| **ESP32 탱크 믹싱** | 링크 A = 왼쪽, 링크 B = 오른쪽, ESP32가 `left = s + t`, `right = s − t` | **채택**: ESP32만 고치면 됨 |
| 메인보드 재빌드 | 믹싱과 부저 수정 | 툴체인과 재플래시가 필요해서 나중으로 미룸(→ 09-22) |
| UARTBUS | 메인보드 4장에 독립 주소 지정 | 4장 재플래시 + 새 프로토콜이라 장기 과제 |

함께 정한 것: 명령 200 미만에서 안 움직이는 구간은 **데드밴드 재매핑**으로 건너뛴다. 램프는 명령
공간에서 그대로 돌리고, 0에서 나오는 첫 틱만 움직일 수 있는 듀티로 점프한다.

### 한 일 3: ESP32 펌웨어 변경 ([src/main.cpp](src/main.cpp))

| 항목 | 구현 |
| --- | --- |
| 구동 모드 | `MODE_BOARD`(메인보드 믹싱) / `MODE_TANK`. 명령 `v <0\|1>`, 웹 셀렉터 |
| 탱크 믹싱 | `turn = steer × max / 1000`, `left/right = clamp(speed ± turn, ±max)`, 프레임의 steer 필드는 0. 양쪽 다 클램프를 넘지 않음 |
| 링크 B 반전 | `i <0\|1>`, 기본은 반전. 좌우 허브모터가 마주 보고 달려서 같은 듀티면 반대로 돈다. 호버보드 마스터가 슬레이브에 `-pwm`을 보내는 것과 같은 이유 |
| 데드밴드 | `b <n>`, 기본 200. `Deadband()`는 0이 아닌 명령을 `[deadband, max]`로 재매핑하고, 결과는 `max`를 넘지 않으며, `max ≤ deadband`면 자동으로 꺼진다 |

## 부록: 포트폴리오 포인트

- **계층 구조가 분명한 시스템**: GD32 메인보드(모터 제어) ← LOLIN D32(안전장치·믹싱·Wi-Fi) ← 상위
  컴퓨터(RDK 장애물 가드 / Jetson 초파리 뇌). 계층마다 책임과 인터페이스(시리얼 콘솔 명령, 9/22바이트
  프레임)가 문서화돼 있어서 다른 머신에서 하루 만에 붙였다(09-17 RDK, 09-18 Jetson).
- **원인을 추측하지 않고 업스트림 소스로 증명**: 룩업 테이블을 그대로 계산해 "안쪽 바퀴 최대 12 %"라는
  수치를 냈다. 그 수치가 사용자의 관측("200 미만은 안 움직임")과 Jetson 실측(1.11 → 0.24 km/h)에 맞물렸다(09-17, 09-18).
- **하드웨어 제약을 소프트웨어로 우회하는 결정**: 메인보드를 구울 수 없는 상황에서 ESP32 쪽 믹싱으로
  문제를 옮겼고, 나중에 한 줄짜리 메인보드 패치(`SLAVE_SAME_SIDE`)로 마무리하는 경로를 설계했다(09-17, 09-22).
- **안전장치를 깨지 않는 확장, 그리고 깨진 사례**: 클램프는 여전히 와이어로 나가는 값을 제한하고, 램프는
  명령 공간에 남겼고, 탱크 모드는 두 링크를 요구한다. 반면 데드밴드는 "잡음 1바이트 = 20 % 듀티"라는
  새 위험을 만들었고, 현장(09-17 RDK)에서 같은 날 드러났다. 기능 추가가 기존 가정("작은 명령은
  무해하다")을 깨는 전형적인 사례다.
- **검증의 층위**: 시뮬레이션(로직) → 실기 시리얼(설정 유지) → 브라우저(UI 호출) → 회귀 테스트 →
  독립 반박 검증을 거친 리뷰 → 다른 머신에서 현장 사용
- **물리 직관을 설명하는 능력**: "슬레이브는 거울 복사"라는 한 문장과 시계 비유로 부호 문제를 이해시켰다(09-22).
- **측정이 판단을 뒤집은 기록(DEBUGGING.md)**: 잘못된 도구가 낸 결론 두 개가 유효한 측정을 덮었던 과정과,
  거기서 뽑은 9가지 규칙
