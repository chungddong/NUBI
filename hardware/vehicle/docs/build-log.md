# 알루미늄 프로파일 모빌리티 베이스 — 설계 기록

build123d(코드로 3D 모델링)로 실내외 테스트용 모빌리티 로봇 베이스를 설계한 과정.
잘 된 것보다 **막힌 것과 틀린 것**을 남기는 데 목적이 있다.

---

## 0. 무엇을 만들려 했나

다목적 테스트 베드다. 하나의 목표가 아니라 **기반**이 필요했다.

- 배달로봇 같은 실내 주행 테스트
- 실외 주행 테스트
- 위에 적재함을 얹거나 로봇팔을 달아보는 실험

즉 "이것도 해보고 저것도 해보는" 플랫폼. 이 성격이 나중에 모든 판단의 기준이 된다.

---

## 1막. 프로파일 단면부터 막혔다

T슬롯 알루미늄 프로파일(2020/3030)을 코드로 그리는 것부터 시작했다.
정사각형에서 T홈 4개를 파내면 될 줄 알았다.

**결과: 단면이 5조각으로 쪼개졌다.**

```
area = 187.59  faces = 5   solids = 5
```

빔 하나를 뽑았는데 솔리드가 5개. 이유는 기하학적으로 단순했다 —
슬롯 4개를 각각 파내면 **코너 기둥이 중심 보스와 완전히 끊어진다.**
+X 슬롯과 +Y 슬롯이 대각선 부근에서 만나 버리기 때문이다.

**해결**: 실물 압출재가 만들어지는 방식 그대로 쌓아 올렸다.

> 바깥벽(튜브) + 코너 기둥 4 + 중심 보스 + 45° 대각 리브 4
> → 슬롯 방은 그 사이에 **저절로** 생기고, 입구만 바깥벽에서 잘라내면 T 홈이 된다.

```
area = 187.59  faces = 1   solids = 1   ✓
```

**교훈**: "빼서 만들기"보다 "실물이 만들어지는 순서대로 쌓기"가 맞을 때가 있다.

## 2막. 프레임이 서다

단면을 라이브러리(`models/tslot.py`)로 분리하고, 빔을 배치해 프레임을 세웠다.

- 400×300×400 연습용 프레임 (빔 12본)
- 이어서 모빌리티 베이스 700×500 (빔 7본 → 최종 18본)

여기서 **자동 검증 3종**을 만들어 붙였다. 이게 이후 모든 걸 구했다.

| 검사 | 방법 | 잡아낸 것 |
|---|---|---|
| 간섭 | 부품군 전 조합 `intersect().volume` | 부품끼리 파고드는 것 |
| 맞댐 | 개별 부피 합 == 합집합 부피 | 겹침 없이 정확히 붙었는지 |
| **연결성** | 전부 fuse 후 **솔리드 개수 == 1** | **공중에 뜬 부품** |

## 3막. 눈에 보이지 않던 것들

### 떠 있던 빔

연결성 검사가 `솔리드 2개`를 뱉었다. 중앙 세로 빔이 **양끝에서 15mm씩 못 미쳐 공중에 떠 있었다.**

```python
CENTER_L = WHEELBASE - 2 * S   # 440  ← 틀림
CENTER_L = WHEELBASE - S       # 470  ← 맞음
```

간섭 검사는 통과했다. 안 닿으니까. **"안 부딪힌다"와 "붙어 있다"는 다른 검사다.**

### 걸터앉은 라즈베리파이

전장 베이 바닥판은 666×486인데, 가장자리 16mm는 **커버 아래 플랜지가 앉는 자리**다.
파이를 그 위에 놓아버렸다.

→ 제원 출력에 **"바닥 유효 634×454"** 를 추가했다. 판 크기 ≠ 쓸 수 있는 크기.

### 라운드 커버가 사각 프레임을 파고든다

측면 커버에 R50 라운드를 주니 **코너에서 프레임 모서리를 파고들었다**(835 mm³).

기하학적으로 필연이다. 반지름 R로 둥글린 사각형이 원래 사각형의 모서리를 품으려면
**0.293 × R 만큼 더 커야 한다.** R50이면 14.65mm.

→ 프레임 외곽선(+1.5mm 여유)만큼 플랜지를 비우는 컷을 넣었다.
직선부는 16mm 플랜지 그대로, 코너에서만 잘린다.

## 4막. 외형과 얼굴

### 상부 프레임이 밖에서 보인다

데크를 바퀴 위로 올리려고 상부 프레임을 750×710으로 크게 잡았더니,
**프로파일이 옆에서 훤히 보였다.**

지적을 받고 상부 프레임을 하부와 같은 700×500으로 줄였다. 그랬더니 부수 효과가 있었다 —
**커버가 프레임을 가로지르지 않게 되어, 커버를 데크 아랫면까지 끝까지 올릴 수 있었다.**
그전까지 "커버 윗단 30mm가 열려 있다"고 적어둔 문제가 통째로 사라졌다.

**설계에서 뭔가를 줄였더니 다른 문제가 같이 풀리는 경우가 있다.**

### 그림자 틈을 수식으로 고정

데크 치수를 커버에서 유도하게 바꿨다.

```python
DECK_L = 2 * SKIRT_X + 2 * DECK_LIP
DECK_R = SKIRT_R + DECK_LIP     # 코너 원 중심이 같아진다
```

→ 데크와 커버의 코너 중심이 일치해서 **직선부든 코너든 틈이 정확히 5mm로 일정**하다.

### 얼굴은 렌더를 보고 두 번 고쳤다

앞면에 카메라(눈) + LED 바(입)를 넣었다. 첫 시도는 계산상 아무 문제가 없었는데,
**선도로 뽑아 보니 눈이 너무 작고 입이 얼굴을 가로질러** 표정이 안 나왔다.

| | 1차 | 수정 |
|---|---|---|
| 베젤 | Ø56 | **Ø76** |
| LED 바 | 400mm | **320mm** |
| 눈·입 간격 | 31mm | **20mm** |

이 세 값이 인상을 거의 다 결정한다. **숫자 검사로는 절대 안 잡히는 종류의 문제다.**

### 벤트를 바퀴 옆에서 앞면으로

흡기 슬롯을 처음엔 측면 커버에 냈는데, 렌더로 보니 **앞바퀴 바로 옆**이었다.
바퀴가 튀기는 물·흙을 정통으로 맞는 자리다.

→ 앞면 LED 바 아래로 옮겼다. 스플래시도 덜 받고, 입 아래 그릴처럼 보여 얼굴도 안 깨진다.

## 5막. 구동계 — 여기서 제일 오래 막혔다

허브모터를 쓰려다 **비용 때문에 포기**하면서 시작됐다.
PVC 통바퀴(Ø210, 12,000원, 볼베어링 내장)를 쓰기로 했는데,
이 바퀴는 **데드 액슬 위에서 도는 물건**이라 "굴리려면 어떻게 하나"가 문제가 됐다.

### 계산이 결정한 것들

스키드 스티어에서는 **제자리회전이 다른 모든 조건을 압도한다.**

```
포장면 주행    0.4 N·m
5% 등판       1.1
잔디·자갈      1.6
제자리회전      4.1   ← 지배 조건
```

그런데 이 계산이 **틀렸다는 지적을 받았다.**

**내가 μ=0.8을 썼다. 고무 타이어 값이다.** 이 바퀴는 PVC다(μ≈0.5).
그리고 제자리회전 토크를 최고속도에서 쓴다고 잡아 출력을 부풀렸다.

정정: 요구 4.13 → **2.58 N·m**, 필요 출력 100W → **30W급**.

### 축간거리라는 레버

스키드 회전 저항은 **축간거리에 정비례**한다.

```
축간 500mm → 4.86 N·m
축간 400mm → 3.89 N·m   (−20%)
```

프레임은 그대로 두고 액슬만 안쪽으로 옮겨서 **공짜로 20%를 벌었다.**
반대로 전폭(윤거)을 줄이면 회전 토크가 **올라간다.** 이 둘은 방향이 반대다.

### 구성 비교

| | 모터 | 회전 시 토크 | 특징 |
|---|---|---|---|
| 4륜 고정 스키드 | 4개 × 3.6 | 회전이 사양을 결정 | 제자리회전 O, 바닥 긁힘 |
| 2륜 + 캐스터 | 2개 × 2.1 | 문지름 없음 | 실내 최적, 캐스터가 실외에 약함 |
| 2륜 + 고정2 | 2개 × 7.2 | **최악** | 둘이 문지름까지 감당 |
| 아커만(앞조향+뒤2륜) | 2개 × 2.5 | 스키드 없음 | **U턴에 1.8~2.3m 필요** |
| 독립조향(스웨어브) | 4구동+4조향 | 1.2 | 8축, +25~40만원 |

**4륜구동인데 바퀴당 토크가 오히려 더 필요한 것**이 직관과 반대라 재밌다.
회전 시 바깥 바퀴는 `추진 + 차동` 을 다 내야 하고, 안쪽 바퀴는 **오히려 제동**을 건다.

아커만은 배달로봇 테스트에 안 맞았다. **엘리베이터와 좁은 복도를 다녀야 하는데 U턴에 2m가 필요**하다.
실제 배달·서빙 로봇이 거의 다 차동구동이나 스키드인 이유다.

## 6막. 모터를 찾아 헤맨 기록

요구: **바퀴 5.48 N·m @ 91 rpm × 4개**

| 후보 | 결과 |
|---|---|
| IG-52GM (국산 유성감속) | 성능 OK, **개당 26만원** |
| JGB37-3530 | 24,000원, **15W** — 토크 1/4 |
| MY1016Z 24V 250W | 3~5만원, **110×110×128mm, 2.5kg** — 안 들어감 |
| PG45-775 (Ø45) | 크기 OK, 30.8W라 **속도 0.5 m/s 제한** |
| Waveshare DDSM210/315/400 | 5.8~12만원, **0.15~0.55 N·m — 10배 부족** |
| SPG S9D90 (90W) | 성능 OK, **Ø80 × 246mm, 감속기가 모터보다 2배 비쌈** |

### SPG 카탈로그를 읽으려고 한 삽질

SPG 사양표가 PDF에만 있었다. 텍스트 추출을 하니 이렇게 나왔다.

```
(&"3&%.0503  →  GEAREDMOTOR
```

**폰트 인코딩이 +31 시프트**돼 있었다. 디코딩해서 목차는 읽었는데,
**숫자만 `¤` 로 나왔다.** 정작 필요한 토크 표가 안 읽힌다.

→ PyMuPDF로 해당 페이지를 **이미지로 렌더링해서 눈으로 읽었다.** 그제서야 표가 나왔다.

### DDSM은 왜 안 됐나

```
DDSM315 정격 0.55 N·m → 제자리회전 가능한 차체 무게 13 kg
우리 차체 52 kg → 4배 초과
```

**감속기가 없는 다이렉트 드라이브**라서 모터 토크가 그대로 바퀴 토크다.
PG45-775는 같은 30W 모터에 50:1 유성기어를 붙여 5 N·m를 만든다. 33배 차이가 여기서 난다.

### 그리고 호버보드

> "전동휠 제품에 들어가는 것도 이런 인휠모터 아닌가?"

이 한마디가 다 풀었다.

```
호버보드 허브모터 8인치   65,000원  (모터뱅크 정품 225,700원의 29%)
36V 250~350W, 3상 BLDC, 15극쌍, 홀센서 120°
1.0 m/s 에서 축토크 21~29 N·m   ← 요구 5.48 의 4~5배
```

- 8인치(≈215mm)가 우리 Ø210과 거의 같다
- **직결이라 감속기·벨트·풀리·데드액슬이 전부 불필요**
- 컨트롤러도 필요 없다 — 호버보드 순정 보드에
  [EFeru/hoverboard-firmware-hack-FOC](https://github.com/EFeru/hoverboard-firmware-hack-FOC)
  펌웨어를 올리면 UART로 제어된다. **보드 1장이 모터 2개**를 돌린다
- 완제품 중고를 사서 뜯으면 **모터 4 + 보드 2 + 배터리 2가 24만원**

사람 100kg를 태우고 언덕을 오르라고 만든 물건이라 토크가 남아돈다.

## 7막. 같은 프레임, 다른 외피

인휠모터로 바꾸기로 한 뒤 "설계를 다시 해야 하나?" 를 물었다. 답은 **아니오**였다.
바퀴 규격(Ø210×58)이 같으니 프레임·데크·커버가 그대로 쓰인다. 바뀐 건 축 마운트뿐.

여기서 외피 변형을 두 가지 만들었다.

| 변형 | 형태 | 바퀴 노출 |
|---|---|---|
| `skirt` | 바퀴 **사이**만 가리는 탈착식 스커트 | 위·옆 노출 |
| `fender` | 바퀴 **위까지** 덮는 두툼한 펜더 | 아래만 노출 |

`LOWER_COVER = "fender"` 한 줄로 갈아끼운다. 이렇게 만들어 두면
"어느 쪽이 나은지" 를 말이 아니라 **렌더 두 장으로** 비교할 수 있다.

그리고 라운드 커버가 사각 프레임 모서리를 파고드는 **0.293R 문제가 또 나왔다**.
스키드 커버에서 한 번, 펜더에서 또, 나중에 스웨어브 셸에서 또. 세 번째에야
공식을 `assert` 로 박아 넣었다.

## 8막. 데크를 모듈식으로

"위에 적재함이든 로봇팔이든 꽂을 수 있게" 라는 요구가 들어왔다.
데크에 **2020 레일 3본**을 200mm 간격으로 얹었다. T슬롯이니 위에 올릴 것도
슬롯 너트로 아무 위치에나 문다. 데크 자체를 다시 뚫을 필요가 없다.

같이 정리한 것: 상단 2D 라이다 목업 제거. 아직 정하지 않은 부품을
모델에 남겨두면 "확정된 설계" 로 오해된다.

## 9막. 방향을 틀다 — 독립 조향

> "이번에는 바퀴가 독립적으로 조향되는 구조로 해보자"

기존 버전은 전부 남기고 `models/swerve_base.py` 를 새로 팠다.
그런데 스키드 프레임을 그대로 못 쓴다. **근본 제약이 하나 있다.**

```
바퀴가 킹핀 둘레로 돌면 반경 √(210² + 58²)/2 = 109mm 원을 쓸고 간다
→ 차체가 바퀴 옆으로 내려올 수 없다
→ 스키드처럼 커버를 z=158 까지 내리면 20° 조향에서 바로 부딪힌다
```

그래서 **층을 갈랐다**. 모듈이 아래(z 0~248), 차체가 위(z 248~).
FRC 스웨어브가 다 이렇게 생긴 이유를 여기서 이해했다. 미학이 아니라 기하학이다.

| | 스키드 | 스웨어브 |
|---|---|---|
| 구동 요구 토크 | 5.48 N·m | **1.24 N·m** (4.4배 감소) |
| 제어축 | 4 | **8** (구동4 + 조향4) |
| 게걸음(crab) | 불가 | 가능 |
| 전고 | 335 | **460** |

스키드의 회전 저항이 통째로 사라진다. 대신 조향계 전부가 새 부품이다.

## 10막. "축이 공중에 떠 있는 거 아니야?"

이 한 문장에 **네 가지 결함**이 들어 있었다. 전부 맞았다.

1. **킹핀축이 프레임에 고정되어 있지 않았다** — 축이 그냥 브라켓 구멍을 통과만 하고 있었다
2. **구멍이 축보다 크니 바퀴가 앞뒤좌우로 흔들린다** — 맞다. 구멍은 베어링이 아니다
3. **조향모터와 축이 연결되어 있지 않았다** — 기어든 벨트든 있어야 한다
4. **애니메이션에서 바퀴와 요크가 서로 겹친다** — 각각 따로 트랙을 걸어서 속도가 달랐다

고친 방식:

```
하중 경로: 프레임 → ㄷ자 브라켓 → 6005 베어링 x2 → 킹핀축 → 요크 → 바퀴
동력 경로: 조향모터 24T → HTD-3M 벨트 → 킹핀 48T (2:1)
```

베어링 2개를 위아래로 띄워 넣으면 반경방향 흔들림과 모멘트가 같이 잡힌다.
빠짐 방지는 칼라 2개. 벨트는 두 풀리 원의 `make_hull()` 로 그렸다.

애니메이션은 **구조로 고쳤다**. 회전부(요크·킹핀축·서스암)를 킹핀이 원점인
Compound 하나로 묶으니 `rz` 트랙 하나가 통째로 돈다. 따로 놀 수가 없다.

이어서 또 한 방:

> "모터도 공중에 떠 있는 구조 아닌가? 상부 프레임에 브라켓 달아야 할 것 같은데"

맞다. 다만 **상부 프레임이 아니라 킹핀 브라켓 위**에 올렸다.
모터를 다른 부재에 달면 조립 오차와 열변형으로 **벨트 센터거리 70mm 가 흔들린다.**
같은 판 위에 있어야 고정된다.

> "앞뒤는 길게 스커트가 내려오게 하지 않아도 되고, 바퀴와 바퀴 사이는
> `--\__/--` 이런 구조로 깔끔하게"

여기서 두 번 헛발질했다.

- **스커트가 통째로 사라졌다** — `Plane.XZ` 의 법선은 **−Y** 다.
  `offset(SHELL_Y+20)` 하고 그 방향으로 밀어 넣으니 프리즘이 모델 **밖으로** 갔다.

  셸은 그보다 아래(z=50)에서 시작하고 있었다. 잘리지 않은 아랫동아리가 남았다.
  **셸 각 짝의 솔리드 개수가 1이 아니라 2** 로 나와서 잡혔다. 또 연결성 검사다.

### 목업을 실물로

가짜 카메라 베젤을 지우고 **ASUS Xtion Pro Live STEP** 을 그대로 얹었다.

눕히는 회전이 필요했다.

```python
orient = Plane(origin=(0,0,0), x_dir=(0,1,0), z_dir=(1,0,0)).location
```

여기서 또 하나 배웠다. 처음엔 실측치를 `(180, 41, 36)` 으로 **반올림해서** 상수로 박았다.

브라켓은 **카메라크로스(3030, 390mm)** 를 기둥 사이에 새로 끼워 그 위에 얹었다.

## 13막. 서스펜션이 실제로는 안 움직였다

이 문서에서 가장 값진 발견이다. 그리고 **아무도 물어봐 주지 않아서** 찾았다.

애니메이션에 바운스를 넣으려고 "몇 도까지 돌려도 되지?" 를 계산하다가,
그냥 믿지 말고 **각도를 스윕하면서 간섭을 재 보자** 고 했다.

```
바퀴 정위치 top = 210 / 요크 수평팔 z 216~224 / MODULE_TOP 230

  암  -2° (바퀴 +3.4mm)   요크x바퀴     265 mm3   ← 기준값
  암  -4° (바퀴 +6.8mm)   요크x바퀴     852 mm3   ← 여기서부터 파고든다
  암  -6° (바퀴 +10.3mm)  요크x바퀴   8,165 mm3
  암 -10° (바퀴 +17.4mm)  요크x바퀴  29,784 mm3
```

**설계값 25mm 트래블이 실제로는 3~6mm 였다.**
요크의 수평팔이 바퀴 바로 위 6mm 지점을 지나가고 있었기 때문이다.

원인은 단순하다. `MODULE_TOP = WHEEL_D + 20` — **눈대중으로 20mm 를 준 것**이다.
서스펜션을 나중에 넣으면서 이 값을 다시 안 봤다.

고친 방식은 값을 키우는 게 아니라 **역산 구조로 바꾸는 것**이다.

```python
YOKE_ARM_Z = WHEEL_D + SUS_TRAVEL + YOKE_CLR + YOKE_T / 2   # 팔은 여기 위에 있어야
MODULE_TOP = YOKE_ARM_Z + YOKE_T / 2 + 2                    # 차체 바닥은 그 위

assert YOKE_ARM_Z - YOKE_T/2 >= WHEEL_D + SUS_TRAVEL + YOKE_CLR, \
    "요크 수평팔이 낮아 서스펜션이 트래블만큼 못 움직인다"
```

이제 `SUS_TRAVEL` 을 바꾸면 차체 높이가 따라온다. 대가는 **전고 442 → 460mm**.

같이 딸려 나온 것 두 개:
- 피벗 보스가 바퀴 폭 안으로 5mm 들어가 있었다 (265mm³)
- 모듈을 올리니 요크 팔이 킹핀 브라켓 수직판을 물었다 (2,640mm³)

### 교훈

**정지 상태 간섭 검사만으로는 부족하다.**
움직이는 설계는 **움직여 보면서** 검사해야 한다. 지금은 스트로크 스윕이
검증 스크립트에 들어가 있다.

## 14막. 배선이 지나갈 길이 없었다

"더 넣을 게 뭐가 있냐"고 묻길래 훑다가 발견했다. **킹핀축이 Ø25 통짜였다.**

인휠모터 한 개가 내보내는 선은 3상(14AWG × 3) + 홀센서(26AWG × 5) = **8선**.
그런데 조향이 ±90° 니까 이 선다발이 **180° 비틀린다**. 지날 구멍조차 없었다.

| 방식 | 판단 |
|---|---|
| 슬립링 | 3상이 20~30A. 대전류 슬립링은 크고 비싸다 |
| 무한회전 | 위와 같은 문제로 되돌아온다 |
| **중공축 + 조향각 제한 + 서비스 루프** | FRC·상용 스웨어브가 다 이렇게 한다 |

Ø25 를 Ø13 으로 뚫으면 벽 6mm. 8선 단면 약 30mm² 가 133mm² 안에 여유롭게 들어간다.

그런데 이 결정이 **세 부품을 한꺼번에 끌고 왔다.**

1. **중공축** — 배선 통로
2. **기계식 하드스톱** — 전자 리밋이 놓치면 선이 끊어진다. 최후 방어선
3. **원점 홀센서** — 전원 넣었을 때 바퀴가 어디 보는지 모르면 못 움직인다

셋은 따로 붙일 수가 없다. 하나라도 빠지면 나머지가 무의미하다.

### 스톱을 세울 자리가 없었다

핀 2개 + 걸림턱 1개로 각도를 제한하는데, 처음엔 하부 칼라 높이에 뒀다.
**요크 수평팔이 바로 거기를 지나간다.** 팔이 핀을 때린다(804mm³).

상부 칼라로 올렸다. 이번엔 위에 **벨트가 있다**(z=300.5~). 그래서 걸림턱은 6mm 만 쓴다.

그리고 각도를 스윕해 봤더니:

```
설계 한계각 ±91.5°
  조향 +90°  브라켓x축   80 mm3  ← 정확히 90°에서 닿는다
```

**작동 범위 끝에서 스톱이 닿으면 스톱이 아니라 방해물이다.**
핀 각도를 벌려 ±99° 로 옮겼다. 이제 ±90° 는 자유롭고 ±95° 부터 걸린다.

```python
STEER_LIMIT = (360 - (STOP_A[1] - STOP_A[0]) - STOP_TAB_W) / 2
assert STEER_LIMIT >= 95, "스톱이 ±90° 조향을 방해한다"
```

### 같이 들어간 것들

- **범퍼 + 리미트 스위치** — 3mm 셸이 직접 부딪히면 깨진다. 밑단에 바를 대고
  플런저가 뒤의 스위치를 누른다. 평시엔 2mm 떠 있다
- **후미등 2** — 앞에 LED 바가 있는데 뒤가 깜깜했다. 비상정지를 피해 좌우로 갈랐다
- **부저** — 앞면 흡기 그릴 뒤에서 운다. 구멍을 따로 안 뚫어도 된다
- **리프팅 핸들 4** — 50kg 인데 잡을 데가 없었다. 데크판(3mm)에 매달면 안 되니
  **상부 사이드 레일 슬롯**에 직결한다
- **주회로 차단기 + 퓨즈·프리차지** — 36V 에 드라이버 커패시터면 인러시가 크다

범퍼를 밑단에 넣으면서 **흡기 그릴이 밀려났다.** 입(LED)과 눈(카메라) 사이로 올렸다.
얼굴 배치는 이제 세 번째 버전이다.

## 15막. 적재함 — 상자를 만드는 데 세 번 막혔다

> "적재함 설계 들어가볼까?" → 820 × 620 × 450, 후면 도어, 화물칸 + 상단 센서 마운트

처음엔 2020 프레임 12본 + 판재로 짰다. 그런데 요구가 하나 더 붙었다.

> "아래 디자인과 일치하게 올라가도록 둥근 모서리 모양이어야 해. 위에 레일에
> 슬라이드로 끼워지는데 슬라이드 구멍은 앞에서 안 보이고 뒤에서만 보이도록,
> 플랫폼과 적재함 사이 빈 공간이 뒤에서 보는 거 아니면 안 보이게."

프레임 방식으로는 라운드 코너가 안 나온다. 셸과 같은 단면(810×610 R60)을 그대로
위로 이어 올리는 프린트 셸로 바꿨다. 그리고 여기서 **세 번 막혔다.**

### 첫째 — 라운드 스커트는 슬라이드가 기하학적으로 불가능하다

스커트를 데크까지 내려 빈 공간을 가리려 했다. 그런데 라운드 코너 때문에 앞으로
갈수록 스커트 안쪽 폭이 좁아진다. 계산해보니:

```
스커트 안쪽 반폭 = 302 - 57 + √(57² - (57-δ)²)
데크 반폭 280 을 통과하려면 δ ≥ 11.4
→ 밀어 넣을 수 있는 거리 45mm
```

**45mm 만 들어간다.** 답은 스커트를 데크까지 내리지 않고 **레일 구간(20mm)만**
덮는 것이었다. 레일은 폭 ±210 이라 코너가 좁아져도 여유가 남는다.
데크 밑단은 1mm 그림자선으로 남겨 "빈 공간"이 아니라 의장선으로 읽히게 했다.

### 둘째 — 닫힌 앞벽은 반드시 레일을 가로지른다

앞벽이 막혀 있으면 밀어 넣는 동안 무조건 레일과 부딪힌다. 레일을 중간에서 끊어봐도
앞벽이 그 지점을 지나가므로 마찬가지다.

답은 **노치**였다. 레일을 셸 면까지 빼고 벽에 레일 단면 크기의 노치를 내면,
노치가 레일을 타고 미끄러져 들어온다. 최종 위치에서 레일 끝면이 노치를 채우므로
구멍이 아니라 마감으로 보인다.

### 셋째 — 방향을 반대로 만들었다

> "슬라이드로 앞에서 뒤로 끼우는 거고 구멍이 뒤에서 보여야 하잖아"
> "그냥 방향만 앞뒤로 바꾸면 되는 거였는데 왜 이렇게 돌아가"

내가 노치를 **앞벽**에 내고 큰 개구를 뒷면에 뚫어놨다. 앞에서 뒤로 밀면 레일이
함의 **뒷면**으로 들어오니, 노치는 뒤에 있고 앞면은 통으로 막히는 게 맞다.
요구사항이 그냥 맞아떨어지는 구조였는데, 반대로 만들고 그걸 맞추려 돌아갔다.

게다가 개구 중심 좌표를 잘못 계산해서 **뒤끝이 아니라 옆면 한가운데**가 뚫려 있었다.

```
잘못:  -(폭)/2 - |SLIDE|/2  = -212.5   →  구간 -252 ~ -172   (옆면 중앙)
맞음:  SLIDE - 폭/2         = -385     →  구간 -425 ~ -345   (뒤끝)
```

### 그 밖에

- **3mm 벽에는 걸침턱을 팔 수 없다** — 뚜껑을 안쪽에 앉히는 리베이트를 10mm 파려다
  벽이 3mm 라 자리가 없었다. 뚜껑은 위에 얹고 안쪽 립으로 위치를 잡는 게 맞다
- **판재 5장이 모서리마다 겹쳤다**(22cm³) — 전부 같은 크기로 만든 탓. 바닥·천장을
  먼저 깔고 옆판이 그 사이, 앞판이 옆판 사이로 들어가게 고쳤다
- **적재함이 앞으로 빠지는 걸 막는 게 없었다** — 채널 스토퍼는 뒤로 밀 때만 멈춘다.
  제동하면 관성으로 216L 짜리가 미끄러져 나온다. 레일 끝 중앙 보어(M5)에 물리는
  **노치 리테이너 3개**를 넣었다. 이건 사용자가 "타이다운이 왜 필요하냐" 물었을 때
  찾았다 — 타이다운(화물↔함)과 리테이너(함↔로봇)는 다른 일을 한다

## 16막. 각진 상자를 부드럽게 — 어깨 라운드

> "적재함이 조금 높아. 그리고 디자인적으로 어떻게 좀 더 귀엽고 친근하게?"

높이를 450 → 360 으로 낮추고, **어깨 라운드 R55** 를 넣었다. 1/4 원을 6단면으로
근사해 loft 로 옆벽에서 윗면으로 곡면을 만든다. 이게 인상을 가장 크게 바꿨다 —
각진 상자에서 둥근 덩어리로 읽힌다.

기능적으로도 이득이었다. **어깨를 뚜껑에 포함**시키면 열었을 때 800×600 전면이
다 열린다. 어깨를 셸에 두면 개구가 690×490 으로 좁아진다.

내부는 "배달 음식 용기처럼 깔끔하게" 라는 요구에 따라 **벽을 3 → 5mm 로 올리고
세로 리브를 없앴다.** 대신 격벽과 라이너 트레이가 보강을 겸한다. 실제로 음식이
닿는 면은 코너 R25 로 둥글린 **탈착 라이너 트레이**다.

격벽(x=230)으로 앞쪽 168mm 를 **장비 베이**로 잘라냈다. 나중에 펠티어 온도제어를
넣는다면 이 구획이 그대로 쓰인다.

## 17막. 손잡이를 세 번 옮겼다

50kg(이라고 믿었던) 기계를 들 손잡이가 없었다. 세 번 옮겼고, **두 번은 사용자가
구조를 지적해서** 옮겼다.

| 차 | 위치 | 왜 틀렸나 |
|---|---|---|
| 1차 | 데크 위 4코너 | 적재함(820×620)이 통째로 덮어버렸다 |
| 2차 | 셸 옆면 상부 | **상부 레일까지 22mm 가 비어 있는데 잇는 부재를 안 넣었다.** 사실상 3mm 프린트 셸에 매다는 꼴 |
| 3차 | 하부사이드 레일 직결, 바퀴 사이 | 하중이 프레임으로 바로 간다 |

> "핸들 자체가 프레임이 아니라 쉘에 붙어있는 것 같은데 이러면 약해서 부서지지 않을까"

정확한 지적이었다. 3차에서 **하중 경로**를 명시했다:

```
손 → 그립 봉 Ø18 → 팔 Ø20 ×2 (셸 Ø24 구멍 관통) → 베이스판 → 3030 하부사이드 레일
```

셸에는 **Ø24 구멍 8개**만 뚫린다. 하중을 안 받는다. 부수적으로 손잡이가 무게중심
높이(z=267) 근처로 내려와 데크 위(460)보다 들기 안정적이다.

처음엔 매립형(봉이 안으로 들어간 형태)으로 만들었는데, 이것도 오해였다:

> "구멍을 저렇게 뚫으란 것이 아니라 작은 구멍을 통해 핸들 봉이 튀어나와서
> 잡을 수 있게 하라는 거였어"

큰 개구 대신 작은 관통공 2개로 봉이 나오는 형태로 바꿨다. 전폭 628 → 712.

## 18막. 무게를 처음으로 제대로 셌다

모듈 후보를 물어보길래 "적재 여력"을 답하려다, 미뤄뒀던 중량 계산을 했다.

```
구조 합계        77.2 kg      무게중심 z = 357 mm
체결류·배선 +15%  약 89 kg     정적 전복각 33~36°

모듈 4세트(허브모터 포함)  20.0 kg   @ z=158
배터리 [추정]             12.0 kg   @ z=326
적재함 일체               17.4 kg   @ z=620
프레임 3030                7.2 kg
판재(데크+베이바닥, Al 3mm) 6.1 kg
```

전에 "50kg대"라고 했는데 **실제로는 89kg** 이다. 적재함(17kg)과 판재를 알루미늄으로
잡은 게 컸다.

이게 두 가지를 바꿨다:
- **좋은 쪽**: 무겁고 낮아서(CG 357) 전복 여유가 넉넉하다. 페이로드를 꽤 높이 올려도 된다
- **나쁜 쪽**: 89kg 은 **두 명이 못 든다.** 핸들 4개는 4인 기준(22kg/인)이다

적재 한계도 여기서 나왔다:

| 한계 | 값 |
|---|---|
| 구동 모터 | 100kg 이상 |
| **서스펜션** | **약 60kg** ← 병목 |
| 전복(25° 유지) | CG 700mm 에서 50kg |

**높이보다 무게가 먼저 걸린다.**

## 19막. 모듈을 규격으로 만들다

적재함 하나를 만드느라 겪은 제약을 다음 모듈에서 또 겪을 이유가 없었다.
그래서 **표준 페이로드 인터페이스**(`docs/payload-interface.md`)를 문서로 고정하고,
슬라이드 부분을 `payload_skirt()` 함수 하나로 뽑아 공유했다.

`PAYLOAD` 파라미터 한 줄로 4종이 갈아끼워진다.

| 모듈 | 내용 | 전고 |
|---|---|---|
| `cargo` | 적재함 810×610×360, 170L, 격벽 + 라이너 + 상부 뚜껑 | 840 |
| `flat` | 평판, M6 100격자 + 타이다운 6 | 504 |
| `sensor` | 3D 라이다 + 팬틸트 + GNSS + IMU, 마스트 삼각화 | 1041 |
| `arm` | 팔 마운트 10mm 판 + 보스 + 리브 3본 + 컨트롤러 | 938 |
| `inst` | 계측 — 로드셀 4 + 시험 플랫폼 + DAQ + 견인 훅 | 605 |

### 센서 타워 — 진동이 적이다

외팔 마스트에 라이다를 얹으면 주행 진동으로 포인트클라우드가 흐려진다.
기둥 2본을 200mm 띄워 Y축 굽힘을, 전후 대각 브레이스 4개로 X축을 삼각화했다.

브레이스 회전 부호를 반대로 줘서 **마스트 밑에서 바깥으로 뻗어 올라간** 적이 있다.
삼각형이 아니라 벌어진 V였다. 베이스판(낮고 바깥) → 마스트(높고 안쪽) 방향이어야 한다.

### 팔 마운트 — 전복이 아니라 서스펜션이 문제였다

```
전복      복원 258 N·m  vs  최대도달 전도 13 N·m  →  여유 19.9배
서스펜션  코너당 4.9mm 처짐 → 기울기 1.07° → 툴 이동 약 19mm
```

전복은 신경 쓸 게 아니었다. 대신 팔이 뻗으면 그 모멘트가 앞뒤 쇼크에 힘 짝으로
전달돼 차체가 1.07° 기울고 **툴이 19mm 움직인다.** 팔의 반복정밀도(±0.1mm)를
200배 무의미하게 만드는 수치다.

**11막에서 "실외 주행 때문에 서스펜션이 필요하다"고 넣은 게 여기서 정면으로 부딪혔다.**
서스펜션과 정밀 매니퓰레이션은 상충한다.

### 아웃리거로 서스펜션을 우회한다

상충을 없앨 순 없으니 **작업 중에만 서스펜션을 빼는** 쪽으로 갔다.

자리를 잡는 데 제약이 하나 있었다. `z < 248` 에서는 **90° 조향 스윕이 x 151~369 를
통째로 쓴다.** 남는 건 바퀴 사이(|x|<151, 앞뒤로 너무 짧다)와 11mm 짜리 틈뿐이다.
그래서 **스윕 위(상부 사이드 레일, z=436)에서 피벗**해 셸 밖으로 내려오는
접이식으로 만들었다. 위쪽은 x 제약이 없어 ±360 까지 벌렸다.

```
접힘   전폭 720   (핸들 712 대비 +8)
전개   전폭 1059,  지지 베이스 720 × 979  (바퀴 520 × 520)
전복각 36° → 좌우 54° / 앞뒤 45°
```

여기서도 한 번 틀렸다. 처음엔 **잭까지 암과 같이 45° 로 기울였다.** 그러면 발판이
지면에 안 닿고 옆으로만 벌어진다 — 전폭 1432 가 나오고 발이 z=64 에서 멈췄다.
실제 아웃리거는 암이 벌어진 뒤 **수직 스크류**가 내려간다.

그리고 아웃리거는 **모듈이 아니라 베이스**에 붙였다. 모듈에 달면 로봇 전체 무게가
슬라이드 인터페이스(레일 슬롯에 2.5mm 물린 턱)를 통과한다. 핸들과 같은 이유다.

## 20막. 검증 코드가 세 번 같은 함정에 빠졌다

`Compound(children=[...])` 는 자식을 **재부모화**한다. 두 개를 미리 만들어 두면
나중 것이 앞 것의 자식을 빼앗아 **앞 것이 텅 빈다.**

이것 때문에:
1. HLR 투영이 **1500선 → 22선**으로 죽었다 (도면이 거의 백지로 나왔다)
2. 뚜껑 여닫힘 렌더에서 2·3번째 장면이 **뚜껑만 남고** 나머지가 사라졌다
3. 슬라이드 시퀀스 렌더에서도 같은 일

세 번 다 "부품이 갑자기 사라진다"는 같은 증상이었는데, 세 번째에야 원인을 잡았다.
뷰마다 그때그때 새로 묶거나, 참조를 먼저 스냅샷해 둬야 한다.

**교훈**: 검증·렌더 코드도 코드다. 결과가 이상하면 모델이 아니라 **검사기를 먼저
의심**해야 한다. 앞서 간섭 검사에서 조상 Location 을 안 곱해 4개가 전부 같은 부피로
겹친다고 나온 것과 같은 종류의 실수다.

## 21막. 스워브를 버렸다

6.5" 호버보드 휠로 스워브를 만든 사례들을 찾아 보고했는데, 돌아온 답이 설계를
접었다.

> "저 구조는 나중에 스프링을 달거나 하기 어려운 구조 같은데, 저 모터를 국내에서
> 당장 구하기도 힘들고"

맞는 지적이었다. 레퍼런스들은 조향·서스펜션·구동을 한 덩이로 묶어 놓아서, 나중에
서스펜션을 끼워 넣을 자리가 없다. 그리고 조달이 안 되는 부품 위에 설계를 쌓으면
그 설계는 종이로 끝난다.

**그래서 서스펜션도 스워브도 없는 고정식 4륜부터 다시 잡기로 했다.**

```
                    스워브        스키드
제어축              8             4        조향 4축이 통째로 사라진다
서스펜션            4세트         없음
전고                595           518
축간                520           420
```

스키드가 제자리에서 돌려면 구동 모멘트가 저항 모멘트를 이겨야 한다.

```
M_저항 = μWL/2      (앞뒤로 끌리는 타이어)
M_구동 = μWT/2      (좌우 역회전)
→ T/L 비가 관건.  지금 520/420 = 1.24
```

축간을 520에서 420으로 줄인 건 이것 때문이다. T/L 이 1.0 이면 겨우 돌고, 1.2 이상이면
여유가 생긴다.

### 교훈

**부품이 사라지면 실패 지점도 같이 사라진다.** 조향 4축을 빼면 조향모터·벨트·베어링·
하드스톱·원점센서·그 배선이 전부 없어진다. 첫 제작에서 이건 순수한 이득이다.
서스펜션은 나중에 이 프레임 위에 얹으면 된다 — 그게 이번 결정의 전부다.

## 22막. 축에 나사가 없었다

브라켓의 축 구멍이 축보다 크다는 걸 사용자가 짚었다.

> "바퀴 끼우는 구멍이 바퀴 축보다 더 크고, 끼우면 안 빠진다는 거야?"

그래서 축 끝에 너트를 그려 넣었다. 그러자 다음 말이 왔다.

> "애초에 보드 축은 너트를 끼울 수 있게 되어 있는 형태는 아닌데 말이야"

**STEP 을 0.1mm 간격으로 스캔해서 확인했다.**

```
X  -51.0 ~ -50.0     지름이 연속으로 줄어든다   → 1mm 모따기
X  -50.0 ~ -46.5     Ø16 원형
X  -46.5 ~  -3.7     Ø16 + D컷 평면 (축중심 +5)
```

**나사부가 없다.** 모따기로 그냥 끝난다. 내가 그린 너트는 존재할 수 없는 물건이었다.

같은 스캔에서 하나 더 나왔다. D컷 **평면** 구간을 −48~−3 으로 가정하고 있었는데
실제는 −46.5~−3.7 이었다. 그 1.5mm 차이 때문에 안쪽 판이 원형 구간을 밟아
34mm³ 간섭이 나 있었다.

`axle_nut()` 를 지웠다. 축을 물 방법은 **클램프뿐**이고, 그건 호버보드에서 떼어낸
실물이 이미 있었다.

### 교훈

**실물 STEP 이 있으면 가정하지 말고 스캔해라.** 이 스캔 한 번이 존재하지 않는
부품 하나와 34mm³ 간섭 하나를 동시에 잡았다. 스캔 코드는 열 줄이었다.

## 23막. 휠 브라켓이 세 번 바뀌었다

레일 밑면(z=170.7)에서 축(z=79.35)까지 **91.35mm** 를 무엇으로 채우느냐 —
이 하나로 세 번 갈아탔다.

### 1차. 판재 브라켓 (CNC 발주용)

클램프판 2 + 타이판 + 플랜지 + 브리지를 한 솔리드로 만들고, 발주를 위해
두께 방향으로 갈랐다. 분해가 맞는지는 부피로 검증했다.

```
원본 141.0 cm3  =  조각 합 141.0 cm3      ← 어긋나면 즉시 잡힌다
```

그런데 사용자가 근본을 물었다.

> "3D 프린팅으로 하기엔 너무 약할 것 같고, 금속으로 하려면 CNC나 금속 3D 프린팅을
> 맡겨야 할 텐데 흠.."

기성품을 찾아보라기에 SHF16/SK16 샤프트 서포트를 내밀었다. 답이 왔다.

> "샤프트 서포트가 왜 나와? 내가 너랑 같은 휠 브라켓을 보고 있는 거 맞나?"

**렌더해 보고 내가 틀린 걸 인정했다.** 그 부품은 91.35mm 를 건너는 물건이지
클램프가 아니다. 나는 "축을 무는 것"만 보고 "그 높이를 채우는 것"을 잊고 있었다.

### 2차. 3030 프로파일 (사용자 아이디어)

> "굳이 가공이 힘든 저런 형태 말고, 휠 브라켓을 그냥 프로파일로 대체할까?
> 프로파일 하단 구멍에 탭 가공만 해서 기존 클램프랑 같이 끼우면 들어가겠는데"

이게 맞았다. 91mm 를 채우는 일은 **프로파일 한 토막**이면 되고, 가공은 끝단 M8 탭
하나뿐이다. 값이 10~50배 싸진다.

### 3차. ㄷ자 마운트 (최종)

프로파일은 레일 **밑면에만** 물린다. 그러면 횡력 모멘트를 볼트가 프라잉으로 받는다.

> "프레임과 아래쪽에서만 고정하는 게 아니라 ㄷ자 형태로 해서 프레임을 안쪽에서
> 감싸는 형태로, 위에서도 고정하고 아래서도 고정하는 방식이 좋을 것 같은데"

레일 높이 30mm 를 팔로 쓰는 **순수 커플**이 된다. 프라잉이 사라진다.

여기서 삽질이 세 번 있었다.

```
기둥을 가운데로 곧게 올림     클램프 앉을 자리를 7,220 mm3 먹었다
                             → x=±30 두 팔로 갈라 클램프를 타고 넘게

치수가 제각각                 블록 깊이 39.22 / ㄷ자 팔 34 / 전폭 65 / 벽 9
                             → 전폭 70 · 깊이 40 · 벽 10 **세 수**로만 유도
                                (사용자: "애매하게 턱이 조금 있거나 해서 애매하거든")

레일 볼트를 기둥 위에 둠      구멍(21.7~28.3)이 기둥(25~35)을 3.3mm 파고들고,
                             아래팔 볼트는 렌치가 기둥에 막힌다
                             → x=±25 → ±15, 공구 여유까지 어서트로
```

마지막 것은 어서트를 **간섭이 아니라 공구 여유**로 걸었다는 게 요점이다.
구멍이 안 물리는 것만으로는 부족하고 렌치가 들어가야 한다.

```python
assert BOLT_X + HEX_R < ARM_X - WALL / 2   # 15 + 6 = 21 < 25
```

## 24막. 남의 STEP 을 재서 알아낸 것들

호버보드에서 떼어낸 클램프의 STEP 을 재다가 설계 전체를 결정한 숫자가 나왔다.

```
채널 깊이 5.07  =  D컷 평면 높이(축중심 +5)
```

**맞대는 면이 정확히 축 중심 높이에 온다.** 그러면 클램프 채널이 평면을 물어
회전을 막고, 우리가 만들 마운트는 **축 아래 둥근 면만 받치면 된다.** 회전 방지를
설계할 필요가 없어졌다.

이걸 모르고 있었을 때 나는 "블록이 D컷 평면 구간 안에 있어야 한다"고 어서트를
걸어 놨었다. 대상이 틀렸다. 평면 안에 있어야 하는 건 **클램프**다.

### 구멍은 원이 아니라 장공이었다

```
장공 8.128 폭 x 16.25 길이     (반원 중심 x=±11.04, ±19.16 → 조정 8.12mm)
중심 (±15.1, ±11.87) 4곳
```

### 그리고 그 8.128 은 실측이 아니다

인치로 바꿔 보고 알았다.

```
코너 R    2.540 = 0.1000"   ← 정확히 떨어진다
필렛 R    0.254 = 0.0100"   ← 정확히
구멍 Ø    8.128 = 0.3200"   ← 정확히
외폭     42.720 = 1.6819"   ✗
두께     12.570 = 0.4949"   ✗
높이     39.220 = 1.5441"   ✗
```

**외형은 실측값이고 반지름·구멍은 모델러가 타이핑한 라운드 인치값**이다.
GrabCAD 사용자 업로드지 제조사 도면이 아니다. 즉 실물 구멍은 8.0 일 수도 8.3 일
수도 있다.

그래서 볼트를 M6 로 정했다.

```
             M8                  M6
장공 통과    여유 0.13mm — 도박   여유 2.13mm — 확실 (와셔 OD 12가 덮는다)
볼트 하중    480 N               480 N   (구동반력 29 N·m / x=±15.1 커플)
볼트 능력    16 kN               11 kN → 23배 여유
블록 살      y쪽 4.73mm          y쪽 5.63mm
```

장공은 **원래 조정용**이라 폭이 헐거워도 기능에 문제가 없다.

여기서도 한 번 틀렸다. 처음 "인치로 떨어지는가" 판정을 너무 헐겁게 짜서 **일곱 줄
전부에 "정확히 떨어진다"가 붙었다.** 1.6819" 는 전혀 라운드가 아닌데도. 판정식을
고치고 나서야 위의 3:4 패턴이 보였다.

### 교훈

**남이 만든 STEP 은 어디까지가 실측인지 물어봐야 한다.** 인치 환산은 그걸 알아내는
싸고 확실한 방법이었다. 그리고 그 답이 볼트 크기를 바꿨다.

## 25막. 만드는 방법을 다섯 번 갈아탔다

같은 부품 하나를 두고 판단이 다섯 번 뒤집혔다. 순서대로 남긴다.

### (1) 3D 프린팅 / 진공주형 / CNC

```
진공주형   ✗   4개 뽑는데 몰드값을 4로 나눈다 (이 공법은 20~200개 구간)
               PU 레진은 상시하중에 크리프. 옥외 여름 표면 60°C 는 HDT 구간
SLA        ✗   취성 + 자외선 + 크리프. 구조부품 + 옥외 = 최악 조합
SLM        ✗   오버킬. CNC 로 못 깎는 형상일 때 쓰는 건데 우리 건 다 깎인다
```

### (2) JLC 견적이 논리를 뒤집었다

국내 가공비 기준으로 "CNC 는 나중에"라고 했는데, 실제 견적이 반대였다.

```
CNC 6061 4개    $228   개당 $57
MJF 나일론 4개  $285   개당 $71
```

말이 되는 결과다. **MJF 는 부피 과금인데 우리 부품은 190cm³ 를 통짜로 채우고,
CNC 는 가공시간 과금인데 우리 부품은 전부 각진 형상에 셋업 2~3회다.** 형상이
우연히 CNC 쪽에 유리했다.

### (3) 학교 CNC — 2.5D 라는 걸 확인했다

```
웹면 실루엣 64.4 cm2 를 Y 로 40 밀면      257.7 cm3
거기서 부품을 빼면 남는 것                 68.1 cm3
   = 포켓 하나(70x30x30.4) + 탭 구멍 4개
```

**이 부품은 2D 단면을 밀어낸 것 + 포켓 하나**다. 게다가 바깥 윤곽이 정확히
70 × 151.35 직사각형이라, 70×40 각봉을 톱으로 자르면 **외곽 가공이 0** 이다.

```
셋업 1   웹면을 바닥에 놓고 위에서 — 관통 슬롯 + 축 시트 + ㄷ자 포켓
셋업 2   +Z 에서 Ø6.6 x4   (위아래 팔이 동축이라 한 번에 뚫린다)
셋업 3   -Z 에서 M6 탭 x4
```

밀링 셋업이 **1회**다. 3축이면 충분하고 4·5축이 필요 없다.

### (4) PLA 로도 되나

계산해 보니 **정적으로는 PLA 가 이겼다.**

```
        파단횡력   여유    접지처짐   인성지표   Tg
PLA      1856 N   8.5배   0.34mm      2.5     60°C
PETG     1519 N   7.0배   0.60mm      7.2     80°C
ASA      1485 N   6.8배   0.57mm      5.3    105°C
```

그런데 **그 질문이 틀렸다.** 마찰이 낼 수 있는 최대 횡력이 218 N 이라 주행으로는
1519 N 에 도달을 못 한다. 유일한 파괴 경로는 **측면 충격**이고, 거기서는 인장강도가
아니라 에너지 흡수가 답이다 — PLA 가 3배 진다.

열은 계산과 무관하게 PLA 를 떨어뜨린다. **허브모터는 축이 곧 고정자**라 코일 열이
그 강철 축을 타고 우리 블록으로 직접 들어온다. Tg 60°C 는 여유가 아니다.

### (5) 결론

**프린트 먼저.** 여유 7배는 정적 기준이고, 우리가 모르는 건 재료 강도가 아니라
옥외 충격하중이다. 그건 CNC 로 바꾼다고 알게 되는 게 아니라 굴려봐야 안다.
깨지면 그때 CNC — 그 시점엔 치수도 확정돼 있다.

## 26막. 프린트 자세를 반대로 알려줬다

처음에 "블록을 바닥에 놓고 세워서" 뽑으라고 적었다. **반대였다.**

```
             바닥접촉   높이    서포트   응력 방향
웹면 눕히기   64.2 cm2   40mm    0        층과 나란함   ← 맞다
세우기        26.5 cm2  151mm   39.6cm2  층간 인장
```

웹면이 **부품 실루엣 전체를 덮는 단일 평면**이라 거기 눕히면 서포트가 0 이다.
더 중요한 건 응력 방향이다. 굽힘 응력이 σ_zz 인데 눕히면 그게 층 안쪽이 되어,
층간 인장 25 MPa 가 아니라 소재 인장 45~50 MPa 를 쓴다. **여유가 8배에서 13배가
되고, 파괴 모드가 층 분리가 아니게 된다.**

그리고 파일 쪽에 문제가 둘 더 있었다.

```
자세      모델이 로봇 좌표라 슬라이서에 넣으면 151mm 세로로 선다
          사람이 손으로 돌리게 두면 언젠가 틀린 자세로 뽑는다
          → bed() 로 눕혀서 바닥 z=0 에 앉혀 내보낸다

파일명    CNC판·프린트판이 둘 다 "휠마운트.step" 이었다
          PRINT 실행이 CNC 파일을 조용히 덮어썼고, 파일만 봐선 알 수 없었다
          → _cnc_M6 / _print_M6 을 박는다

DXF       눕힌 부품을 로봇 좌표 평면으로 자르고 있었다 (43 → 7 cm2, 하나는 아예 없음)
          → 프린트판에서는 DXF 를 안 낸다. 가공용이라 의미도 없다
```

### 교훈

**자세·단위·좌표계는 파일에 박아서 내보내라.** 사람이 매번 맞추게 하면 언젠가
틀린다. 그리고 산출물 이름에 조건을 안 박으면 조용히 덮어쓴다 — 이건 며칠 뒤에
발견하면 원인을 못 찾는 종류의 버그다.

## 27막. 30.000 은 안 끼워진다

ㄷ자 슬롯 높이가 정확히 **30.000mm** 였다. 레일도 공칭 30 이니 맞는 것처럼 보인다.

**프로파일 압출 공차가 ±0.2~0.3 이다.** 레일이 30.2 로 나오면 안 들어간다.
프린트면 줄로 밀면 그만인데, **알루미늄 4개를 받아놓고 안 들어가면 답이 없다.**

여유를 주는 방향도 정해져 있었다.

```
위팔 밑면 = 레일 윗면에 딱      볼트가 미끄러지면 수직하중을 여기서 걸려 받는다
여유는 아래팔 쪽으로만          조이면 스프링너트가 팔을 레일 면으로 당겨 닫힌다
```

폭(Y) 공차는 신경 쓸 필요가 없다는 것도 확인했다. **ㄷ자가 Z 로만 감싸고 +Y 쪽이
열려 있어서 레일이 두꺼워도 갇힐 데가 없다.**

검증하다 두 번 헛짚었다.

```
1차   레일 상자를 중심 기준으로 키웠다 → 위로도 자라 위팔에 닿았다
      실제로는 레일 윗면이 위팔 밑면에 붙는다
2차   높이와 함께 폭까지 키웠다 → 웹에 닿아 간섭으로 잡혔다
      물릴 수 있는 건 높이뿐인데 폭을 같이 흔들었다
```

높이만 흔들어서 다시 재니 깔끔했다.

```
CNC   슬롯 30.4   레일 30.4 까지 OK, 30.5 부터 물림
PRINT 슬롯 30.8   FDM 내부치수가 0.1~0.3 작게 나오는 것까지 얹음
```

### 교훈

**"공칭이 같다"는 맞는 게 아니다.** 그리고 끼워맞춤 검증은 **어느 축이 물릴 수
있는지 먼저 정하고** 그 축만 흔들어야 한다. 다 같이 키우면 물리지 않을 축에서
가짜 간섭이 나온다.

## 28막. 도면 스크립트가 사라져 있었다

도면을 다시 뽑으려고 보니 **이미지 41~47 은 있는데 만든 코드가 없었다.**
예전 세션에서 즉석으로 돌리고 저장을 안 한 것이다.

그 대가가 이미 나 있었다. 모델은 스키드로 바뀐 지 한참인데 **도면만 스워브 시절
치수(전고 595 / 축간 520)로 굳어 있었다.** 고칠 방법이 없으니 아무도 안 고쳤다.

`models/drawings.py` 로 다시 짰다. HLR 은선제거 6면 투영이다.

여기서도 한 번 틀렸다. 4개 입면이 좌우로 잘렸는데, 축척 중심을 **점 평균**으로
잡은 게 원인이었다. 곡선은 48분할이고 직선은 2점이라 선이 촘촘한 쪽으로 중심이
끌려간다. bbox 중심으로 바꿔 해결했다.

바퀴는 **실물 STEP 을 기본**으로 뒀다. 이 프로젝트 관례는 "렌더는 목업"인데
도면만 예외다.

```
목업   4.6s/면 · 6면 27초 · 선 1,108개
실물  23.0s/면 · 6면 111초 · 선 3,278개    ← 트레드와 허브 스포크가 산다
```

남한테 주는 문서라 111초는 싸다.

### 교훈

**산출물이 아니라 산출하는 코드를 남겨라.** 이미지만 남으면 그 이미지는 그 순간
박제되고, 모델이 바뀌어도 아무도 못 고친다. 이 문서에서 유일하게 "잃어버린 것"이
이거였고, 잃어버린 줄도 몰랐다.

| 외장 셸이 붙어 있다고 봄 | **세 번째로** 떠 있었다 | 사용자가 "고정 파츠가 안 보인다" |

| D컷 평면 −48~−3 | **−46.5~−3.7**. 눈대중으로 옮겨 적었다 | 안쪽 판이 원형 구간을 밟아 34mm³ |

| ㄷ자 슬롯 30.000 이면 맞는다 | 압출 공차 ±0.3. **레일이 30.2 면 안 들어간다** | 발주 직전에 공차를 따져 봄 |
| 도면은 이미지가 남아 있으니 됐다 | 만든 **코드가 없어서** 모델이 바뀌어도 못 고친다 | 다시 뽑으려다 스크립트가 없는 걸 발견 |
| "인치로 딱 떨어진다" 판정 | 임계값이 헐거워 **일곱 줄 전부**에 붙었다 (1.6819" 에도) | 결과가 전부 참이면 그건 판정식이 틀린 것 |
| 끼워맞춤 검증에서 상자를 통째로 키움 | 물릴 수 있는 건 **높이뿐**인데 폭·중심까지 흔들어 가짜 간섭 | 30.2 레일이 "안 들어간다"고 나옴 |

**이번 구간에서 반복된 건 "가정을 실측으로 착각하는 것"이다.** D컷 평면, 클램프
구멍, 프로파일 공차 — 셋 다 "그럴 것이다"를 "그렇다"로 쓰고 있었다. 실물 STEP 을
0.1mm 로 스캔하거나 인치로 환산해 보는 데 드는 비용은 각각 십 분이 안 됐다.

**"떠 있음"이 세 번 반복됐다.** 형상을 만들면 자동으로 붙는다고 착각하기 쉽다.
CAD에서 `add()` 는 **위치**만 정하지 **결합**을 정하지 않는다.

그리고 마지막 줄이 제일 무섭다. **검증 코드 자체가 틀릴 수 있다.**
결과가 "너무 규칙적"(4개가 전부 같은 부피)이면 그건 신호다.

## 30. 방법론 — 무엇이 실제로 오류를 잡았나

### 숫자 검사
- 부품군 전 조합 **간섭 검사** — 조상 Location 을 누적해 **월드 좌표**로 비교해야 한다
- 맞댐 검사(개별 부피 합 = 합집합)
- **연결성 검사(솔리드 개수 = 1)** ← 떠 있는 빔, 떠 있는 셸 조각을 잡은 유일한 수단

### 움직임 검사   (13막)
정지 상태만 보면 서스펜션이 0mm 만 움직여도 통과한다.
**각도를 스윕하면서** 간섭 부피를 찍으면 "어디서부터 물리는지" 가 그래프로 나온다.

```
  암  -2°  요크x바퀴    265 mm3   ← 기준(정상 결합부)
  암  -4°  요크x바퀴    852 mm3   ← 여기서부터 문제
```

### 그림 검사   (12·28막)
OCC의 **은선 제거(HLR)** 로 2D 선도를 뽑아 눈으로 본다.

```python
visible, hidden = shape.project_to_viewport(eye, viewport_up=(0, 0, 1))
```

잡은 것: 5조각으로 쪼개진 T슬롯 단면, 얼굴로 안 읽히던 작은 눈,
앞바퀴 옆의 흡기 슬롯, **통째로 사라진 스커트**.

숫자로는 안 잡히는 종류다. 간섭 0이어도 못생기거나 아예 없을 수 있다.

### 실물 측정   (22·24막)

가정을 실측으로 착각하는 게 이번 구간의 주된 실수였다. 싸게 확인하는 방법 둘.

**(1) STEP 을 0.1mm 로 스캔한다.** 축 단면을 0.1mm 간격으로 잘라 지름을 찍으면
어디까지가 D컷이고 어디부터가 모따기인지 그냥 보인다.

```
X  -51.0 ~ -50.0   지름이 연속 감소   → 1mm 모따기 (나사부 아님)
X  -46.5 ~  -3.7   Ø16 + 평면        → 여기만 회전을 막을 수 있다
```

존재하지 않는 부품(축 너트) 하나와 34mm³ 간섭 하나를 이 스캔 한 번이 잡았다.

**(2) 남의 모델은 인치로 환산해 본다.** 어디까지가 실측이고 어디부터가 타이핑인지
갈린다.

```
코너 R 2.540 = 0.1000"  정확   |  외폭 42.720 = 1.6819"  ✗
구멍 Ø 8.128 = 0.3200"  정확   |  두께 12.570 = 0.4949"  ✗
```

**반지름·구멍은 모델러가 친 값이고 외형만 실측이다.** 이 한 줄이 볼트 크기를
M8 에서 M6 로 바꿨다.

### 계산은 모델에서 뽑고, 해석해로 교차검증한다   (25막)

강도 계산에서 단면계수를 손으로 어림하지 않고 형상을 잘라서 재고, 그 값을 손계산과
맞춰 봤다.

```python
fs = (mount & Plane(origin=(0,0,z))).faces()
BRepGProp.SurfaceProperties_s(f.wrapped, prop)
Ixx += prop.MatrixOfInertia().Value(1,1) + f.area*(cy_f - cy)**2   # 평행축 정리
```

```
OCC 결과   Ixx 106,667 / Zx 5,333
손계산     2 × 10×40³/12 = 106,667      ← 일치
```

이게 맞아떨어져야 **반원 시트가 파인 블록** 같은 손으로 못 푸는 단면의 값도 믿을 수
있다. 처음엔 평행축 정리를 빼먹어 Iyy 가 726,667 대신 6,667 로 나왔는데, 교차검증이
없었으면 그대로 갔을 것이다.

그리고 **어디까지가 계산이고 어디부터가 인용인지 갈라 적어야 한다.**

```
확실   단면 성질      모델 형상에서 나왔고 해석해와 일치
표준   굽힘 공식      교과서. 가는 보가 아니라 오차 10~20%
가정   89kg / μ=1.0   로봇이 60kg 이면 전부 비례해 바뀐다
인용   재료 물성      데이터시트 통상값. 프린트 실물은 ±30% 흔들린다
안 함  충격력         계산하지 않았다 ← 결론이 여기 걸려 있는데도
```

### 판정식이 전부 참이면 판정식을 의심하라   (24·27막)

"인치로 딱 떨어지는가" 를 검사했더니 **일곱 줄 전부에 참이 나왔다.** 1.6819" 처럼
전혀 라운드가 아닌 값에도. 임계값을 잘못 잡은 것이었다.

같은 종류로, 끼워맞춤 검증에서 레일 상자를 중심 기준으로 통째로 키웠더니 물릴 수
없는 축(폭)에서 가짜 간섭이 나왔다. **어느 축이 물릴 수 있는지 먼저 정하고 그 축만
흔들어야 한다.**

### 검사기를 먼저 의심하라   (20막)

결과가 이상할 때 모델이 아니라 **검사·렌더 코드**가 틀린 경우가 반복됐다.

- 간섭 검사가 조상 Location 을 안 곱해 "4개가 전부 같은 부피로 겹침" → 결과가
  **너무 규칙적**이면 그건 신호다
- `Compound(children=...)` 재부모화로 뷰가 텅 빔 → "부품이 갑자기 사라짐"이
  세 번 반복됐는데 세 번째에야 원인을 잡았다

**검증 코드도 코드다.** 같은 증상이 두 번 나오면 검사기를 뜯어봐야 한다.

### 설계에 assert 를 심는다

```python
assert YOKE_ARM_Z - YOKE_T/2 >= WHEEL_D + SUS_TRAVEL + YOKE_CLR   # 트래블이 진짜 나오나
assert SKIRT_TOP_X <= KINGPIN_X - SWEEP_R - SWEEP_CLR             # 스커트가 스윕 원 침범
assert SHELL_X - SHELL_T >= BASE_L/2 + 0.293*(SHELL_R - SHELL_T)  # 라운드 코너 0.293R
assert _fin_y < TOP_RAIL_Y < SHELL_Y - SHELL_T                    # 플랜지 볼트가 레일 위인가
```

**파라메트릭 설계의 진짜 이점은 "치수를 쉽게 바꾸는 것"이 아니라
"바꿨을 때 깨지는 곳을 자동으로 아는 것"이다.**

### 산출물이 아니라 산출하는 코드를 남긴다   (28막)

도면 41~47 은 이미지만 남고 만든 스크립트가 없었다. 그래서 모델이 스키드로 바뀐
뒤에도 **도면만 스워브 시절 치수로 굳어 있었다.** 고칠 방법이 없으니 아무도 안 고쳤고,
잃어버린 줄도 몰랐다.

지금은 `models/drawings.py` 가 있고, 모델을 고치면 다시 돌리기만 하면 된다.
같은 이유로 휠 마운트의 원본은 `models/wheel_mount.py` 한 곳이고 `swerve_base.py`
가 그걸 import 한다 — 두 벌로 그리면 반드시 어긋난다. 접합면에는 좌표계가 틀어지면
즉시 죽는 assert 를 걸어 뒀다.

더 나아가 **값을 직접 쓰지 말고 역산하게 만드는 게 낫다.**
`MODULE_TOP = WHEEL_D + 20` 은 assert 로도 못 잡는다. 애초에 근거가 없기 때문이다.

여기에 서스펜션 4세트와 카메라 6개가 얹혔다.

### 폭이 넓은 이유

가격 범위가 3배 가까이 벌어지는 건 **조향 모터 하나 때문**이다.

- 최소안: NEMA17 + 유성감속 + 자석 엔코더 (약 25,000/개)
- 최대안: 브러시리스 서보 (약 150,000/개)

스웨어브 조향은 **절대각 위치 제어**가 필요하다. 전원을 넣었을 때 바퀴가
어디를 보고 있는지 알아야 한다. 싸게 가면 영점 복귀 루틴을 직접 짜야 하고,
비싸게 가면 그냥 된다. **여기가 다음에 결정할 지점이다.**

### 주의할 것 두 가지

1. **프린트 물량이 많다.** 학교 프린터가 1000³ 이라 **분할은 필요 없다**
   (셸 한 짝이 810 × 610 × 293). 지금 앞뒤 2분할은 출력이 아니라 **조립** 때문이다 —
   닫힌 고리를 프레임에 씌울 수 없다. 다만 필라멘트가 공짜여도 출력 시간은 아니다.

   ```
   외장셸      2,656 cm³  (앞뒤 각 1.3 리터, 짝당 60~80시간)
   적재함 일체  약 14 리터 — 벽 5mm 이라 재료가 크게 늘었다
   ```

   적재함 쪽이 훨씬 크다. 줄이려면 **평면부(옆·앞·바닥·지붕)를 3mm 판재로 빼고
   라운드 코너·림만 프린트**하는 하이브리드가 답이다. 대략 절반으로 준다.
2. **공차 중량은 아직 안 셌다.** 스키드에서 32kg 이라고 했다가 40kg 으로 정정한
   전례가 있다. 조향계·서스펜션이 얹혔으니 **50kg 대**로 보는 게 맞다.

1. **"코드로 3D 모델링을 한다고?"** — build123d 소개, T슬롯 단면 그리기
2. **"단면이 5조각으로 쪼개졌다"** — 첫 좌절과 발상 전환
3. **"안 부딪히는 것과 붙어 있는 건 다르다"** — 검증 자동화, 떠 있던 빔
4. **"로봇한테 얼굴을 달아주자"** — 카메라와 LED 바, 렌더 보고 두 번 고친 이야기
5. **"모터 하나 고르는 데 왜 이렇게 오래 걸리지"** — 후보 6종 전멸기
6. **"PDF가 안 읽혀서 이미지로 렌더링했다"** — SPG 카탈로그 삽질
7. **"AI가 틀렸다고 되물었더니"** — μ=0.8, 중량 32kg, 볼트 320세트
8. **"전동휠 모터 쓰면 되잖아?"** — 213만원이 33만원이 된 순간
9. **"바퀴가 따로따로 돌면 어떨까"** — 스웨어브로 갈아타기, 109mm 원이 만든 층 구조
10. **"공중에 떠 있는 거 아니야?"** — 세 번 반복된 같은 실수
11. **"움직여 보기 전엔 몰랐다"** — 트래블 25mm 가 실제로는 3mm 였던 이야기
12. **"상자 하나 만드는 데 세 번 막혔다"** — 라운드 스커트는 슬라이드가 불가능하다는 계산
13. **"방향만 뒤집으면 되는 거였는데"** — 노치가 앞이 아니라 뒤에 있어야 하는 이유
14. **"손잡이를 세 번 옮겼다"** — 3mm 셸에 50kg 을 매달고 있었다
15. **"무게를 처음 셌더니 89kg"** — 50kg 이라 믿었던 것
16. **"서스펜션이 팔의 정밀도를 200배 망친다"** — 앞에서 넣은 게 뒤에서 부딪히다
17. **"검사기가 세 번 같은 함정에 빠졌다"** — Compound 재부모화
18. **"스웨어브를 버렸다"** — 스프링 못 다는 구조 + 국내 조달 불가, 제어축 8→4
19. **"축에 나사가 없었다"** — 있지도 않은 너트를 그리고 있었다, 0.1mm 스캔
20. **"휠 브라켓이 세 번 바뀌었다"** — CNC 판재 → 프로파일 → ㄷ자 마운트
21. **"남의 도면을 인치로 바꿔봤더니"** — 8.128 = 0.32", 실측이 아니라 타이핑
22. **"자세를 반대로 알려줬다"** — 세워라 → 눕혀라, 서포트 40cm² 가 0 이 되는 이유
23. **"30.000 은 안 끼워진다"** — 공칭이 같다는 건 맞는 게 아니다
24. **"도면 스크립트가 사라져 있었다"** — 이미지만 남기면 박제된다
25. **"그래서 얼마 들었나"** — 구 스키드 vs 현행 vs 스웨어브 BOM

### 영상에 쓸 만한 장면
- 5조각으로 쪼개진 T슬롯 단면 vs 고친 단면 (선도 비교)
- 얼굴 1차 vs 2차 (눈 크기 차이) → 3차: 가짜 베젤이 실물 Xtion 으로 바뀌는 컷
- **스커트가 통째로 사라진 렌더** (Plane.XZ 법선 사고)
- 각도 스윕하면서 간섭 부피가 265 → 852 → 8,165 → 29,784 로 튀는 화면
- 비용이 213만 → 151 → 90 → 33만원으로 내려갔다가, 스웨어브에서 다시 오르는 그래프
- `assert` 가 걸려서 빨갛게 터지는 화면
- 도면이 거의 백지로 나온 화면 (HLR 1500선 → 22선)
- 뚜껑이 열리는 애니메이션, 모듈 4종이 슬라이드로 갈아끼워지는 시퀀스
- 축을 0.1mm 씩 스캔하며 지름이 찍히는 화면 — 모따기 구간이 드러나는 순간
- 클램프 치수를 인치로 환산하니 반지름·구멍만 딱 떨어지는 표
- 세운 자세 vs 눕힌 자세 — 서포트 39.6cm² 가 0 이 되는 비교
- 스워브 모듈이 통째로 걷히고 ㄷ자 마운트 하나로 바뀌는 컷 (전고 595 → 518)
- JLC 견적 화면 — CNC $228 이 나일론 $285 보다 싼 순간

도면(41~47)은 `models/drawings.py` 가 만든다. 은선제거(HLR) 6면 투영이라
모델을 고치면 다시 돌리기만 하면 된다 — 예전엔 이 스크립트가 저장이 안 돼서
모델이 스키드로 바뀐 뒤에도 도면만 스워브 시절 치수로 남아 있었다.

```bash
.venv/Scripts/python.exe models/drawings.py
```

바퀴는 실물 STEP 이 기본이다 (6면 111초). 배치만 빠르게 볼 때는 `HUB_MOCK=1`
(27초), 한 면만 볼 때는 `ONE=정면`. 페이로드를 바꿔 뽑으려면 `PAYLOAD=...`.
