첫날 저녁 20:04~21:24 KST 구간이다. 프레임·데크·라운드 커버까지는 앞 구간에서 서 있었고, 이 구간에서는 커버 표면에 실제 기능 요소를 올렸다 — 후면에 비상정지와 커넥터 도어, 전면에 카메라와 LED 바, 그 다음 환기·배선 관통부·배터리 고정. 중간에 ocp_vscode 뷰어 UI가 깨져 보이는 문제를 한 번 조사했고, 마지막에 도면식 렌더를 어떻게 만드는지 설명하는 것으로 끝났다. 파일은 전부 models/mobility_base.py 하나다.

20:04 후면 패널 — 비상정지 + 포트 도어

커버 뒤쪽에 E-Stop 버튼이 들어갈 구멍과 버튼을 만들어주고 그 하단부에는 연결포트등을 꽂을 수 있는 공간과 커버를 같이 만들어주라

막힌 것: 기존 커버는 좌/우 두 짝으로 나뉘어 있어 분할선(y=0)이 후면 한가운데를 지났다. 비상정지와 포트를 세로 중앙에 놓을 수 없었다.

해결: 분할을 앞/뒤로 바꿨다. 후면이 통판이 되어 배치가 대칭으로 떨어진다. 대신 후면 커버를 떼면 배선이 딸려 나오므로 여유 루프를 두거나 중간 커넥터를 물려야 한다는 조건이 새로 생겼다.

  • 비상정지: 22mm 표준 취부공 Ø22.3 + 회전방지 홈, 중심 z=272. 머리 Ø40이 커버 면에서 24mm(칼라 4 + 머리 20) 돌출. z=272는 임의값이 아니라 몸체 뒤끝(z=289)이 상부 크로스멤버 아랫면(z=298)에 닿지 않는 최대치다.
  • 포트 도어 170×80 @ z=200, M4 4개, 커버 바깥면에서 2mm 돌출. 비상정지는 항상 눌러야 하므로 도어 밖에 뒀다.
  • 커넥터 구멍은 별도 판 없이 2mm 커버 판에 직접 뚫었다 — 패널마운트 커넥터가 그대로 물리는 두께다.

20:32 뷰어 UI 깨짐 조사 — 서버가 아니라 브라우저 캐시

뷰어가 이렇게 왼쪽 위에 버튼이나 아래 트리에서 버튼등이나 제대로 로딩이 안된거마냥 안보이거든? 뷰어를 다시 시작해야하나?

재시작 전에 뭐가 안 불러와졌는지부터 봤다. 포트를 보니 3939를 잡은 것은 시스템 파이썬 프로세스(PID 15760, Python312\python.exe -m ocp_vscode)였고 venv에서 띄운 21100은 포트 없이 따로 떠 있었다. Claude 쪽 브라우저 패널의 콘솔에는 에러가 없었고 Small view, collapsing tree가 6번 찍혀 있어 패널을 1600×950으로 키워 봤다(사용자 브라우저와는 별개 창이라 결론은 못 냈다). venv에는 ocp_vscode 4.0.0이 있었고, 시스템 파이썬에서 import ocp_vscode는 ModuleNotFoundError였다. 여기까지 조사했을 때 사용자가 끼어들었다.

시크릿창에서 접속해서 보면 제대로 Ui 가 보이네

이 한 줄이 결정적이었다. 시크릿창 = 캐시 없음 = 정상, 일반창 = 캐시 있음 = 깨짐. localStorage·sessionStorage도 비어 있었고, Claude가 확인한 바로는 콘솔 에러 0건에 JS·CSS·아이콘 SVG가 전부 200 OK였다. Claude는 원인을 브라우저 HTTP 캐시로 잡고 해결로 Ctrl+Shift+R을 제시했다. 그러면서 "근본 원인은 따로 있다"며 앞서 본 포트·import 결과를 근거로 "존재하지 않는 설치본으로 예전에 뜬 유령 프로세스(15760)가 시기별로 다른 버전 파일을 같은 URL로 서빙해 캐시가 꼬였다"는 진단을 덧붙였다. 사용자가 "다 죽이고 새로 띄우자"고 해서 두 프로세스를 죽이고 venv로 다시 띄웠는데, 20초 대기 후 3939를 잡은 것은 또 시스템 파이썬(PID 9696)이었고 그 부모가 venv 프로세스(9992)였다.

정정: 원래 있던 15760도 venv 프로세스의 정상적인 자식이었고 "유령 프로세스·버전 불일치" 진단은 근거가 없었다. 서버 재기동은 해서 나쁠 게 없었을 뿐 필요한 조치가 아니었다. 당시에는 이것을 "ocp_vscode가 venv에서 띄워도 실제 서버를 시스템 파이썬 자식으로 띄우는 구조"라고 적었는데, 청크 안에서 그 이유까지 밝히지는 않았다. 검수 시 보태는 설명: 현재 저장소의 .venv/pyvenv.cfg는 home = ...\Python312를 가리키고 .venv/Scripts/python.exe는 274 KB짜리 런처다. Windows venv의 python.exe는 기본 인터프리터를 자식으로 띄우는 리디렉터라 부모(venv 경로)/자식(Python312 경로) 쌍이 나오고, 그 자식은 venv의 site-packages를 본다. 직접 실행한 Python312\python.exe는 venv 밖이라 import가 실패했을 뿐이다 — ocp_vscode 고유 구조가 아니라 venv 일반 동작으로 보이지만, 당시 프로세스로 직접 확인한 것은 아니다. 재기동 직후 콘솔에 WebSocket error가 반복해서 찍혔지만 모델 전송 자체는 Using port 3939로 정상 진행됐다.

20:58 환기·배선·배터리 브라켓 — 간섭 두 번, 선제 수정 한 번, 자리 이동 한 번

21:20 도면식 렌더 방식 설명

사용자가 렌더 방식을 물었다. OCC의 은선 제거(HLR)로 2D 엣지를 뽑아 matplotlib으로 선만 그린 것이다. 핵심은 shape.project_to_viewport((2600, 0, 250), viewport_up=(0, 0, 1))이 visible/hidden 엣지를 갈라 주고, 각 엣지를 e @ t로 29점 샘플링해 폴리라인으로 그리는 것 — 직선·원호·스플라인을 가리지 않는다. 아이소는 (1200, -1600, 850) 시점. 원근 투영이라 앞바퀴가 뒷바퀴보다 크게 나온다.

이걸 쓰는 이유는 Claude가 ocp_vscode 화면을 볼 수 없어서다. 실제로 이 렌더로 잡은 것이 T슬롯 단면 5조각 분열(앞 구간), 눈이 작아 얼굴로 안 읽힌 것, 흡기 슬롯이 앞바퀴 옆이던 것 — 셋 다 숫자 검사로는 안 잡히는 종류였다. 한계도 적었다: 치수선·단면·표제란이 없어 도면처럼 보일 뿐 도면은 아니고, 시점이 너무 가파르면 엣지가 일부 빠진 적이 있다. 진짜 도면은 ExportSVG / ExportDXF로, 판금 5종(커버 2, 데크, 바닥판, 마운트 판, 포트 도어)은 DXF로 뽑아 레이저 업체에 넘길 수 있다고 제안했다.

  • 비상정지는 포트 도어 밖. 커넥터 구멍은 별도 판 없이 2mm 커버 판에 직접.
  • 얼굴 세 값: 베젤 Ø76 / LED 320 / 간격 20 — 렌더를 보고 정했다.
  • 흡기는 측면이 아니라 앞면 LED 아래, 배기는 후면 80mm 팬 2개.
  • 배터리 고정은 바닥판 50mm 격자에만 볼트 — 배터리가 바뀌어도 앵글만 옮긴다. 배터리 위치는 축간 정중앙.
  • 뷰어는 venv 하나만 띄운다. 프로세스가 venv/시스템 파이썬 둘로 보이는 것은 정상이다. UI가 깨져 보이면 먼저 시크릿창으로 확인하고 Ctrl+Shift+R.

현재 저장소와의 차이

현재 저장소(2026-09-15 검수 시점)의 mobility_base.py는 07-28에 0.90 축소된 판이라 이 구간 값과 다르다: 하부 프레임 700×500 → 630×450, 축간 500 → 400, 커버 바깥 740×550 → 670×490, 바퀴 Ø200 허브모터 → Ø210 PVC 통바퀴 + 데드 액슬(구동계 미정), LED 슬롯 320×16 → 290×16(안쪽 플랜지 314×34), 흡기 슬롯 y ±160/±80/0 → ±145/±72/0, 바닥판 그로밋 (±200, ±150) → (±150, ±150), 중량 집계 항목명 "모터마운트/바퀴+허브모터" → "액슬마운트/바퀴 4개(모터 별도)". build-log 31절의 최종 사양은 전장 700 × 전폭 632 × 전고 335, 축간 400 / 윤거 564다. 비상정지(z=272, Ø22.3, 머리 Ø40), 포트 도어(170×80 @ z=200)와 포트 6종, 카메라(Ø76 베젤, z=262, PCD 60), LED 중심 z=196, 흡기 슬롯 60×6 @ z=172, 팬(80mm, Ø76, PCD 71.5, z=200), 배터리 260×170×90과 브라켓 볼트 자리는 지금도 같다. venv의 ocp_vscode는 지금도 4.0.0이다.

남긴 일

  • 허브모터 STEP 또는 축·폭 도면 — 마운트 판·윤거·커버 여유 8mm를 실물 기준으로 다시 잡아야 한다.
  • 배터리·드라이버·온보드 컴퓨터·라이다·카메라 실물 치수.
  • 앞면 흡기 슬롯은 완전 방수가 아니다 — 스펀지 필터 또는 물끊기 립.
  • 팬은 80×80×25 대표 몸체와 Ø76 구멍만 넣었다. 실제 팬 모델(두께·커넥터) 미정.
  • 후면 커버 탈거 시 배선 여유 루프 또는 중간 커넥터.
  • 비상정지 머리가 데크보다 19mm 밖 — 가드 여부.
  • 하중 검증(적재 40kg 기준 볼트 전단, 데크 처짐, 무게중심)은 아직 안 했다.
  • 판금 5종 DXF 내보내기 스크립트(제안만).

교훈

  • 간섭 0·솔리드 valid는 형상이 맞다는 뜻이 아니다. 얼굴 비례, 흡기 위치, 플랜지 위에 걸터앉은 부품은 전부 그림을 봐야 잡혔다.
  • 뷰어 문제에서 "시크릿창에서는 되는가"가 서버/클라이언트를 가르는 가장 빠른 실험이었다. 포트·프로세스를 뒤진 조사는 틀린 "근본 원인"으로 이어졌고, 사용자의 한 줄이 맞았다. 확신 없는 진단은 그렇게 표시하고, 틀리면 정정을 남긴다.
  • 판을 관통하는 부품(그로밋)은 부피가 겹치는 게 당연하므로 처음부터 판을 무는 형태로 모델링해야 간섭 검사가 의미를 가진다. 그 대신 플랜지가 판 위로 솟아 전고 같은 외형 치수를 바꾼다.
  • "바닥판 736×546"과 "장비를 놓을 수 있는 704×514"는 다르다. 제원에 유효 범위를 따로 적어야 다음 배치에서 같은 실수를 안 한다.
