# 시스템 개요

누비의 계층 구성과 계층 사이의 인터페이스를 정리한 문서입니다. 2026-10-13 기준입니다. 아래 두 곳의 내용을
요약했고, 세부 사항은 그쪽 문서가 기준입니다.

- 차체 설계와 부품 선정: [차체 설계 결정 기록 DECISIONS.md](../../hardware/vehicle/models/vehicle/DECISIONS.md) (D-NN)
- 바퀴 제어기: [wheel-controller README](../../firmware/wheel-controller/README.md),
  [ISSUES](../../firmware/wheel-controller/ISSUES.md), [작업 일지](../worklog/README.md)

## 계층

```
상위 컴퓨터   Jetson Orin Nano
   │  USB 시리얼 115200, 텍스트 명령
   ▼
바퀴 제어기   LOLIN D32 (ESP32)
   │  UART 19200 8N1 ×2 (링크 A · B), 바이너리 프레임
   ▼
모터 보드     호버보드 2세대 분리형 보드 ×4 (마스터 + 슬레이브 2쌍)
   │  3상 + 홀센서
   ▼
구동         6.5" BLDC 허브모터 ×4, 스키드 스티어
```

| 계층 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 상위 컴퓨터 | 센서 처리, 장애물 판단, 주행 명령 생성 | 바퀴 하나하나의 듀티 계산 |
| 바퀴 제어기 | 명령 클램프 · 램프 · 데드맨 · 호스트 워치독, 탱크 모드 좌우 믹싱, 폰 조종 페이지 | 인식, 경로 계획 |
| 모터 보드 | BLDC 정류, 보드 모드에서 속도 · 조향 믹싱, 텔레메트리 송신 | 상위 명령 해석 |

## 차체 구성 (차체 설계 기준)

차체 설계 v20 ~ v28에서 고른 부품입니다. 상태는 DECISIONS.md를 따릅니다(확정 / 잠정 = 실물 확인 전).

| 항목 | 부품 | 결정 |
| --- | --- | --- |
| 컴퓨터 | NVIDIA Jetson Orin Nano 개발킷 | D-07 · D-12 |
| 모터 드라이버 | 호버보드 원래 보드 4장 + RoboDurden Gen2.x 펌웨어, 보드당 전류 제한 7 A | D-03 잠정 |
| 뎁스 카메라 | Orbbec Gemini 336 ×2 (앞 · 뒤), 0.3 ~ 3 m | D-02 확정 |
| 2D 라이다 | LDROBOT STL-19P (센서 모듈, 스캔 높이 526 mm) | D-17 잠정 |
| IMU | iAHRS RB-SDA-v1 (USB, 지자기 보정 끔) | D-06 확정 |
| GNSS | GPS630 (u-blox M8). RTK는 나중 | D-17 잠정 |
| 배터리 | 36 V 10S 20 Ah, 최대 방전 30 A. 최고 속도 1.5 m/s로 제한 | D-04 잠정 |
| 전원 변환 | 12 V (Jetson · 컨택터 코일), 5 V (ESP32 · 팬 · LED · USB 허브) | D-07 확정 |
| 비상정지 | DC 컨택터로 바퀴 보드 전원만 끊음. 컴퓨터는 유지 | D-05 확정 (D-19에서 재검토 중) |
| 기타 | 전조등 MR16 ×2 (ESP32 PWM), 상태 표시등, 배기 팬 | D-09 · D-11 · D-17 |

USB는 카메라 2대만 Jetson에 직접, 나머지(라이다 · GNSS · IMU · ESP32)는 유전원 허브를 거칩니다 (D-20).

지금까지 실험에서 쓴 센서는 이와 달리 ASUS Xtion 깊이 카메라 하나였습니다.

## 인터페이스 1 — 상위 컴퓨터 ↔ 바퀴 제어기

USB 시리얼(CH340), 115200, 줄 단위 텍스트 명령입니다.

| 명령 | 동작 |
| --- | --- |
| `s <n>` | 목표 속도 |
| `t <n>` | 목표 조향 |
| `x` 또는 빈 줄 | 정지 |
| `m <n>` | 클램프 상한, 0..1000 |
| `w <0\|1>` | 호스트 워치독 켜기/끄기 |
| `h` | 하트비트 (워치독만 갱신) |
| `v <0\|1>` | 구동 모드: `0` 보드 모드, `1` 탱크 모드 (플래시에 저장) |
| `i <0\|1>` | 탱크 모드에서 링크 B 반전 (저장) |
| `b <n>` | 데드밴드 듀티, `0`이면 끔 (저장) |
| `l <n>` | LED/상태 비트 |
| `?` | 도움말과 현재 설정 |

상위 컴퓨터 쪽 래퍼는 두 가지가 만들어져 있습니다.

- RDK `autocar/hoverlink.py` — 포트 자동 탐색, 텔레메트리 파싱, `w 1` + 250 ms 간격 `h`
- Jetson `fly/hover_link.py` — `drive(v, ω)` (+v 전진, +ω 좌회전, ROS 규약)

ROS 2로 옮기면 이 둘을 하나의 `cmd_vel` 브리지 노드로 합치는 것이 자연스럽습니다.

## 인터페이스 2 — 바퀴 제어기 ↔ 모터 보드

UART 19200 8N1, CRC16-XMODEM(poly `0x1021`, init `0x0000`, 리틀 엔디언).
모터 보드 펌웨어는 RoboDurden Hoverboard-Firmware-Hack-Gen2.x (`2.1.8 master uart.bin`, plain UART 빌드)입니다.

| 방향 | 크기 | 시작 바이트 | 내용 |
| --- | --- | --- | --- |
| 제어기 → 보드 | 9 B | `'/'` (0x2F) | 속도 −1000..1000, 조향 −1000..1000, 마스터/슬레이브 상태 비트 |
| 보드 → 제어기 | 22 B | `0xABCD` | 좌우 속도(100× km/h), 전압(100× V), 좌우 전류(100× A), 좌우 오도메트리(홀 스텝) |

보드는 약 10 Hz로 먼저 텔레메트리를 보내고, 제어기도 10 Hz로 명령합니다. 링크 A는
GPIO16/17, 링크 B는 GPIO26/27입니다. 마스터 ↔ 슬레이브 헤더의 + 핀은 12 ~ 15 V이므로 ESP32에
물리면 안 됩니다 (D-03).

## 구동 모드

| | 보드 모드 (`v 0`, 현재 기본) | 탱크 모드 (`v 1`) |
| --- | --- | --- |
| 링크 구성 | 링크마다 마스터 + 슬레이브 한 쌍 | 링크 A = 왼쪽, 링크 B = 오른쪽 마스터 |
| 믹싱 | 모터 보드가 함 | ESP32가 함: `left = speed + turn`, `right = speed − turn` |
| 제자리 회전 | 안 됨 | 됨 |
| 상태 | 4륜 회전 확인 (바퀴 띄움) | 구현만 함, 지상 주행 전 |

보드 모드에서는 풀 조향 시 안쪽 바퀴가 최대 약 12 % 역방향 듀티만 받는데, 이 모터는 약 20 %는
있어야 움직이므로 회전이 약합니다. 4륜에서 탱크 모드를 쓰려면 메인보드 커스텀 펌웨어
(`SLAVE_SAME_SIDE`)로 같은 쪽 앞 · 뒤 바퀴를 한 짝으로 묶어야 합니다. 이 점은 차체 설계 D-03과
어긋나므로 아래 "정해야 할 것"에 적었습니다.

## 안전장치 (바퀴 제어기)

- **클램프** — 부팅 시 상한 400/1000. 데드밴드 재매핑까지 포함해 와이어로 나가는 값을 제한
- **램프** — 속도 변화 100 ms당 20, 조향 100 ms당 100. 정지는 램프 없이 즉시
- **데드맨** — 텔레메트리가 끊기면 명령을 0으로
- **호스트 워치독** — `w 1`로 켜면 하트비트가 끊길 때 정지 (기본은 꺼짐)

## 차체 설계가 바퀴 제어기에 요구하는 것

차체 설계 결정에는 ESP32가 맡는 일로 적혀 있지만, 펌웨어에는 아직 없는 기능입니다.

| 요구 | 근거 | 펌웨어 |
| --- | --- | --- |
| 보드 전원 핀(`DISABLE_BUTTON`)을 GPIO로 켜고 끄기 | D-03 · D-05 | 없음 |
| 컨택터 출력 전압 감지 → 끊기면 속도 0 + 래치 | D-05 · D-20 | 없음 |
| 전조등 PWM (MOSFET 모듈) | D-11 | 없음 |
| Jetson 명령이 끊기면 정지 | D-03 | 호스트 워치독 있음. 기본이 꺼짐이라 켜는 쪽으로 바꿀지 검토 |
| 비상정지 시 "정지 유지" 먼저, 컨택터 차단은 나중 | D-19 제안 (결정 대기) | 없음 |
| 메인보드 전류 제한 `DC_CUR_LIMIT` 보드당 7 A | D-03 · D-04 | 메인보드 빌드 설정 (ISSUES H1 재빌드 때 반영) |

## 상위 컴퓨터 실험 현황

| 보드 | 환경 | 한 것 |
| --- | --- | --- |
| RDK "sunrise" | aarch64 Ubuntu 22.04, ROS 2 Humble | Xtion 깊이 카메라 전방 장애물 가드 → ESP32 시리얼 인터록 (2026-09-17) |
| Jetson Orin Nano 8 GB "dongki" | JetPack 6.2, CUDA 12.6 | 초파리 전뇌 시뮬레이션 폐루프 주행, 바퀴 띄움 (2026-09-18) |

Xtion은 약 50 cm 안쪽 깊이가 0으로 나오므로, 가드에서는 유효 픽셀이 10 % 미만이면 BLIND로 보고
정지 처리했습니다.

차체 웹 시뮬레이터에서도 점유 격자 + A* + 순수 추종으로 자율주행을 돌려 보았습니다. 복도 27 m를
60 s에 도착했습니다 (D-19, [sim/](../../hardware/vehicle/models/vehicle/sim/README.md)).

## 알려진 문제

바퀴 제어기 전체 목록과 우선순위는 [wheel-controller ISSUES](../../firmware/wheel-controller/ISSUES.md)에 있습니다.

- CH340이 포트를 열 때 흘리는 잡음 바이트가 `speed 1`로 해석되고, 데드밴드 때문에 실제 20 %
  듀티로 움직입니다. 콘솔 입력 강건화가 먼저입니다.
- 상위 프로세스가 강제 종료되면 호스트 워치독이 켜진 채 남아 폰 조작이 막힙니다.
- 조향 응답이 약 0.5 s 늦습니다 (조향 램프 + 상위 루프 5 Hz).
- 텔레메트리 L/R과 실제 왼쪽/오른쪽 바퀴의 대응이 문서마다 다르게 적혀 있어 실측으로 확정해야
  합니다.
- 메인보드가 몇 분 유휴 상태면 스스로 꺼집니다 (D-03도 8분 무동작 꺼짐 설정 확인을 요구).

## 정해야 할 것

- **4륜 보드를 어떻게 짝지을지** — 차체 설계 D-03은 앞축 · 뒤축 단위로 짝을 짓고 두 짝에 같은
  (속도, 조향)을 보냅니다(= 보드 모드). 그런데 바퀴 제어기 실측(2026-09-17 ~ 22)에서는 보드 모드로는
  제자리 회전이 안 되고 회전이 약했습니다. 그래서 제어기 쪽은 같은 쪽 앞 · 뒤를 한 짝으로 묶고
  메인보드 펌웨어에 `SLAVE_SAME_SIDE` 패치를 넣는 탱크 4륜을 다음 단계로 잡아 두었습니다(ISSUES H2).
  D-03은 "같은 쪽 앞/뒤로 묶으면 꼬인다"고 적었는데, 이 패치가 바로 그 문제를 푸는 방법입니다.
  시뮬레이터의 사각지대 분석(D-19 ①)도 제자리 회전을 전제로 합니다. 지상 주행 시험 결과로 정하고 D-03을 개정합니다.
- **D-19 결정 대기** — 옆 낮은 장애물 센서 추가, 비상정지 방식("정지 유지 + 상선 단락").
- **12 V 변환기 용량** — 12 V 예산이 약 4.6 A로 변환기 5 A에 빠듯합니다 (D-11). 한 단계 큰 것으로 바꿀지 정합니다.
- **D-21 진행 중** — 배선을 바닥판 위 직각 경로로 (판 닿음 2, 전선끼리 겹침 69 해결 필요).
- **RDK 보드의 역할** — 차체 설계는 Jetson 한 대 기준입니다. RDK를 계속 쓸지 정합니다.

차체 설계 결정은 DECISIONS.md(D-NN)에, 여러 계층에 걸친 결정은 [decisions/](../decisions/)에 기록합니다.
