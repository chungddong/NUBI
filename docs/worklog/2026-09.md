#### "왜 조향이 안 되는가": 업스트림 소스 분석

`Hoverboard-Firmware-Hack-Gen2.x-GD32/HoverBoardGigaDevice/Src/main.c`를 직접 읽고 pwm 모드
(`DRIVING_MODE 0`)의 믹싱을 수식으로 정리했다.

```
expo       = 1 − |speed| / 2000                  // 속도가 오를수록 조향을 절반까지 축소
steer'     = steer × expo
angle      = 90° − steer' × 0.09
x          = lookUpTableAngle[angle]              // 0°→ −1, 45°→ 0.3, 90°→ 1.0, x(90+k) = 1 / x(90−k)
outer      = speed
inner      = x × speed                            // 곱셈이라 speed = 0이면 조향도 0
STAND_STILL_THRESHOLD = 50                        // |명령| < 50은 0으로 처리
```

풀 조향(1000)일 때 안쪽 바퀴 듀티(업스트림 룩업 테이블로 계산):

| speed | 바깥 | 안쪽 |
| --- | --- | --- |
| 200 | 200 | −109 |
| 300 | 300 | **−120 (최대)** |
| 400 | 400 | −99 |
| 600 | 600 | −17 |
| 1000 | 1000 | +300 |

결론은 네 가지다.

1. 곱셈식이라서 제자리 회전 명령이 존재하지 않는다.
2. 안쪽 바퀴의 역회전 듀티는 최대 12 %인데 이 모터는 ~20 % 아래에서는 움직이지 못한다. 그래서
   안쪽 바퀴는 서서 끌리고, 바깥 바퀴는 200~300으로 기어가는 수준이 된다.
3. expo 때문에 고속에서는 조향 폭 자체가 줄어든다. 사람이 타는 호버보드에 맞춘 튜닝이다.
4. 부저는 `config.h`의 `#define BEEP_BACKWARDS` + `FlagStatus beepsBackwards = SET`으로 컴파일 때 정해진다.
   9바이트 명령 프레임에는 관련 필드가 없어서 ESP32에서 끌 수 없다. `speed < -50`인 쪽이 항상 울리므로
   장착 방향을 바꾸는 트릭도 통하지 않는다.

다음 날(09-18) Jetson 실측이 이 분석과 맞았다. `s +150`, `t +500`에서 마스터 바퀴는 1.11 → 0.24 km/h로
감속만 했다.

## 2026-09-17 (목) · 상위 제어: 전방 장애물 가드

> 시간: 15:47 ~ 16:38 · 장소: RDK 보드 "sunrise" · 날짜 근거: 타 머신 · 관련 이슈: N1, N3, U1, R7 · 원본: 바퀴 제어기 작업 일지 `firmware/wheel-controller/WORKLOG.md`

이 펌웨어는 "호버보드 부품으로 만든 4륜 자율주행 차량"의 바퀴 제어 계층이다. 위 계층은 다른 머신에서
작업했고, 그쪽에서 이 펌웨어에 대해 찾아낸 것을 여기 옮긴다.

```
Xtion ──depth 30fps──► guard.py (ObstacleDetector → Debouncer) ──USB serial 115200──► LOLIN D32 ──UART──► 호버보드
```

### 한 일

- `obstacle.py`: ROI 그리드 깊이 판정(CLEAR/SLOW/STOP/BLIND), 바닥 제거
- `hoverlink.py`: 포트 자동 탐색, 텔레메트리 파싱, `w 1` + 250 ms마다 `h`
- `guard.py`: STOP → `x x` + `m 0`, SLOW → `m 150`, CLEAR → `m 400`. 1 s마다 재전송, 링크가 끊기면 재접속
- ESP32를 `/dev/ttyUSB0`에 물려 끝에서 끝까지 동작을 확인했다(호버보드 전원은 끈 상태).

### 결정

- 인터록에 `m 0`을 쓰는 이유: 펌웨어는 마지막에 쓴 쪽이 이기므로(last-writer-wins) `x`만 보내면 폰
  페이지가 다시 출발시킨다(R7). 대신 STOP 중에는 후진도 막히므로 전진만 막는 인터록 `o <n>`이
  필요하다는 요구가 나왔다(N3).
- Xtion은 ~50 cm 이내에서는 깊이가 0이다. 유효 픽셀이 10 % 미만이면 BLIND로 보고 STOP으로 처리한다.

### 발견한 문제

#### 이 펌웨어에 대해

1. 포트를 `dtr=False`로 열면 ESP32가 리셋된다(Linux에서 확인). hoverctl.py의 열기 순서와 같은 문제다(U1).
2. **CH340이 포트를 열 때 흘리는 잡음 바이트가 라인 버퍼에 남아 `1x` → `atoi` → `speed 1`이 되고,
   데드밴드 재매핑 때문에 바퀴가 실제로 20 % 듀티로 움직인다(N1).** 그쪽은 `stop()`이 `x\nx\n`을
   한 번에 보내도록 우회했다. 근본 해결은 펌웨어에서 해야 한다.
3. 다음 단계로 합의한 것: 콘솔 강건화(비출력 문자 무시, 개행 없이 오래 남은 부분 라인 폐기, 맨 숫자 =
   속도 단축 제거), `o <n>` 전진 전용 인터록(가드 하트비트가 끊기면 해제), RDK에 PlatformIO를 설치해
   거기서 플래시

#### 하드웨어 구성 논의, 핵심 통찰

**슬레이브는 마스터와 반대 부호를 받는다**(`SendSlave(-pwmSlave)`). 호버보드는 두 바퀴가 마주
보게(거울상) 달려 있어서, 반대 부호가 곧 "같은 진행 방향"이다. 모터는 "전진"을 모르고 자기 기준의
회전 방향만 안다는 점을 시계에 비유해 설명했다.

| 슬레이브 위치 | 결과 |
| --- | --- |
| 마스터 건너편 (축 쌍) | 같이 전진 ✅ (현재 구성) |
| 마스터와 같은 편 (좌/우 라인) | 슬레이브가 후진 ❌ |

그래서 케이블만 바꿔서 좌/우 라인으로 묶는 것은 **불가능**하다. 정리한 선택지:

| | 작업 | 비고 |
| --- | --- | --- |
| A. 2륜 탱크 | 슬레이브 케이블 분리, 뒤 축 모터 케이블 맞바꿈(뒤왼 마스터가 뒤오른 모터를 구동), 링크 B 배선, `v 1` | 케이블만 바꾸면 됨. 대각선 2륜(앞왼 + 뒤오른) |
| B. 4륜 탱크 (모터 개조) | A + 라인마다 슬레이브 모터 하나를 상선 2개 + 같은 색 홀선 2개를 맞바꿔 역회전 | 홀 커넥터가 몰딩이라 핀만 바꿀 수 없음 → 선을 자르고 교차하거나 연장 케이블이 필요. 절단은 부담스러워서 보류 |
| C. 메인보드 펌웨어 | 마스터에서 부호 반전 제거 | **채택 예정** (한 일 3) |
| D. UARTBUS | 메인보드 4장 독립 | 장기 과제 |

임시 운용: 보드 모드(`v 0`)로 두고 **뒤 마스터를 링크 B(GPIO26/27/GND)에 연결**하면 4륜 구동은
되지만 조향은 지금 수준 그대로다. 그나마 잘 도는 조건은 속도 500~600 + 풀 조향(안쪽 바퀴 ≈ 0,
바깥 60 %)이다.
