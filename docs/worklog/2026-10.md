## 2026-10-13 (화) · 바퀴 제어: ESP32 바퀴 모드 — 보드 · 탱크 모드를 없애고 믹싱을 ESP32로, N1 수정

> 시간: 16:10 ~ 16:30 · 장소: PC (`F:\Develop\NUBI`) · 날짜 근거: 세션 · 관련 이슈: N1, H2, H3, N4 · 결정: [ADR 0001](../decisions/0001-wheel-board-pairing.md)

모터 보드 마스터를 믹싱 없이 바퀴별 값을 그대로 구동하는 빌드(passthrough)로 바꾸기로 하고([ADR 0001](../decisions/0001-wheel-board-pairing.md),
메인보드 펌웨어 자체는 저장소 밖에서 관리), 그에 맞춰 ESP32 펌웨어를 바꿨다. 프레임 `iSteer`의 의미가 바뀌므로 메인보드보다 먼저 해야 하는
단계다. 빌드와 오프라인 검증까지 했고, 보드에는 올리지 않았다.

### 한 일

#### `src/main.cpp`: 바퀴 모드 하나로

- 보드 모드(`v 0`), 탱크 모드(`v 1`), `v` 명령, 링크 B 반전(`invb`), `STEER_SIGN`을 없앴다. 남은 것은 한 가지다.
  `left = speed + turn`, `right = speed − turn`(`turn = steer × max / 1000`)을 계산해서, 두 링크에 같은
  (`iSpeed` = 왼쪽 = 마스터 바퀴, `iSteer` = 오른쪽 = 슬레이브 바퀴)를 보낸다.
- `i <0|1>`를 "좌우 바꿈"으로 바꿨다(NVS 키 `swap`). 마스터가 실제로 오른쪽 바퀴면 `i 1`로 명령과 텔레메트리를 같이
  맞춘다(H3). 옛 NVS 키 `mode` · `invb`는 지우지 않고 읽지도 않는다. `Preferences::remove()`는 키가 없으면 부팅마다
  오류 로그를 남기기 때문이다.
- 데드맨: 링크 A(앞축)는 필수, 링크 B(뒤축)는 첫 프레임 뒤에 합류하게 했다(옛 보드 모드와 같다). 축 하나에 좌우가 다
  있어서 앞축만으로도 직진하므로, 앞 마스터만 먼저 굽는 시험 순서와 맞는다. 탱크 모드처럼 "둘 다 필수"일 이유가 없다.
- 리포트 끝 `out A B` → `out L R`, `/api/status`의 `outA/outB/mode/invb` → `outL/outR/swap`.

#### N1: 콘솔 입력

- 출력할 수 없는 바이트(0x20 미만, 0x7E 초과)는 줄에 넣지 않고 호스트 워치독도 갱신하지 않는다. 넘친 줄은 잘라서
  실행하지 않고 통째로 버린다. 숫자만 보내는 속도 단축 명령(`atoi`)은 없앴다.
- `Still()`: 시리얼과 웹 모두 `|s|` · `|t|` < 50이면 0으로 처리한다(메인보드 `STAND_STILL_THRESHOLD`와 같은 규칙).
  조향도 넣은 이유: 바퀴 모드에서 `t 20`이 데드밴드를 거치면 ±20 %로 제자리 회전한다.
- 저장소 도구(hoverctl · speedsweep · test_stop · ledtest)와 RDK · Jetson 래퍼는 모두 글자로 시작하는 명령만 쓴다
  (일지 09-17 · 09-18 확인). 단축 명령을 없애도 영향이 없다.

#### 웹 페이지

- 구동 선택 · B 반전 · 조향 반전 칸을 빼고 "좌우 바꿈"(펌웨어 NVS)을 넣었다. 속도 반전은 브라우저 설정으로 남겼다.
- 텔레메트리를 ①좌/①우/②좌/②우 → 앞좌/앞우/뒤좌/뒤우로 바꿨다. 좌우 바꿈을 켜면 L/R이 바뀌어 보인다.

#### 문서

- wheel-controller README(Drive modes → Wheel mixing, 명령 표, Safety, Split boards), `system-overview.md`(계층 표,
  명령 표, 프레임 표, "구동 방식", 알려진 문제, 정해야 할 것), `firmware/README.md`, ISSUES(N1, 다음 할 일)
- 여러 계층에 걸친 결정이라 [ADR 0001](../decisions/0001-wheel-board-pairing.md)로 남겼다. "결정을 기다리는 것"에서
  보드 짝짓기를 뺐다.

### 확인한 것

- 빌드: RAM 14.0 %, Flash 61.5 %(805,909 B). 경고 없음.
- 파이썬 모델(ESP32의 `Still` · `Ramp` · `Deadband` · 믹싱 → passthrough `Pilot()` → `SendSlave(-pwmSlave)`)로 확인했다.
  - 클램프 200/400/700/1000 × 데드밴드 0/200 × 명령 격자(50 간격): 실패 0. 어느 모터 입력도 클램프를 넘지 않고,
    바퀴 진행 방향과 크기가 의도한 좌우 값과 같다.
  - max 400, 데드밴드 200 기준:

    | 명령 | 왼쪽 | 오른쪽 |
    | --- | --- | --- |
    | `s 300` | +350 | +350 |
    | `t 1000` | +400 | −400 |
    | `s 300` + `t 500` | +400 | +250 |
    | `i 1`일 때 `t 1000` | +400 | −400 (프레임만 뒤바뀜) |
  - 정지에서 출발: 첫 틱 210, 이후 틱마다 +10. 데드밴드 점프가 그대로다.

  - `(x, x)`는 옛 보드 모드의 "속도 x, 조향 0"과 모터 입력이 같다(마스터 −x, 슬레이브 +x).

  브라우저 창은 로컬 파일 스크립트를 못 돌려서 화면 렌더링은 확인하지 못했다.

- GPT에는 위치 좌표와 라이다를 주지 않는다. 진짜 위치는 행동 실행(실물에서는 바퀴 오도메트리 · IMU 몫)과 채점에만.
- 장애물 정지는 GPT가 아니라 차 쪽(깊이)에서 한다. GPT는 걸음마다 한 번 부르고, 걸음 사이 움직임은 차가 닫힌 루프로.
- API 키와 프롬프트는 서버에만 둔다. 외부 패키지(openai)를 더하지 않는다.

### 확인한 것

- 모의 모드(API 없이, 가장 트인 화살표로 1.5 m): 입구에서 걸음 4번에 (5.7, −0.3) m까지, 걸음마다 사진 → 화살표 →
  서버 → 실행이 돈다. 걸음 3에서 사람이 범퍼 앞에 오자 깊이로 섰다.
- 보낸 사진: 색이 화면과 같고(선형 → sRGB 변환), 화살표 7개가 바닥 위에 그려진다. JPEG 약 85 KB.
- 서버 요청 모양은 가짜 응답으로 오프라인 시험: 모델 · `reasoning.effort` · `json_schema` strict · 이미지 detail high,
  응답의 `output_text` 해석, 비용 계산(입력 2,500 · 출력 800 토큰, gpt-6.1-sol → $0.013). 진짜 위치는 프롬프트에 없다.
- 키가 없으면 패널에 "OpenAI API 키가 없다"가 뜨고 외부로 아무것도 보내지 않는다.
- 17 cm 렌즈로 본 것: 복도 입구에서 1280 픽셀 사진을 1.6배로 키워도 돌출 표지판 글자는 안 읽힌다. 문 위 번호판은
  문 앞에서 시야 밖(위로 32.5°까지만 봄). GPT는 문 개수 · 생김새와 층 안내로 추론해야 한다.

### 발견한 문제

- 실물에서도 같은 문제가 생긴다: 앞 카메라가 17 cm 높이면 호실 번호판과 표지판 글자를 거의 못 읽는다. 카메라를 위로
  기울이거나, 높은 곳에 카메라를 하나 더 두거나, SfM 지도 위치 인식에 기대야 한다.
- 시뮬레이터 복도는 텍스처를 코드로 그려 실제 사진과 다르다. 이 시험은 'GPT가 카메라만으로 길을 찾나'를 보는 것이지
  실제 화면 인식 정확도가 아니다.

  세기와 바닥선 거리 어림으로 했지만, 눈가림 시험은 아니다. 공정한 비교는 API 모델(같은 프롬프트)로 해야 한다.
- `agent_claude.py` 오프라인 시험(가짜 클라이언트): 이미지 → 글 순서, `thinking` · `effort` · `json_schema`, Opus는

## 2026-10-13 (화) · 상위 제어: Jetson 유선 직결 — USB로 들어가 이더넷 고정 IP

> 시간: 20:30 ~ 20:55 · 장소: PC, Jetson "mokpo" (계정 `dongki`) · 날짜 근거: 세션

PC와 Jetson을 랜선으로 직결했는데 서로 보이지 않았다. 직결에는 DHCP 서버가 없어 Jetson 유선이 주소를 못 받고
기다리고 있었다. USB-C 장치 모드(`192.168.55.1`)로 들어가 Jetson 유선에 고정 IP `192.168.127.2/24`를 넣고 PC를
`192.168.127.1/24`로 되돌려, 이더넷으로 핑 · SSH가 된다.

### 한 일

> 이 컴퓨터에 젯슨 장치를 이더넷 통해서 연결했거든? 확인해볼래?

- PC `이더넷`(Realtek GbE)은 1 Gbps 링크, 주소는 고정 `192.168.127.1/24`. `192.168.127.2 ~ 254` 핑에 ARP 응답이 하나도
  없었다. Jetson 쪽에서는 링크가 바뀔 때 브로드캐스트 24 · 멀티캐스트 8개가 들어오고 그 뒤 조용했다. UDP 67 대기,
  mDNS 질의(IPv4 · IPv6)에도 응답 없음.

> 음 지금 이더넷 설정이 자동으로 받기가 아니라서 그럴지도?

- PC를 자동으로 바꾸자 PC는 `169.254.117.169`(APIPA)를 받았지만 Jetson은 그대로 안 보였다. 우분투 NetworkManager는
  DHCP가 안 되면 IPv4 링크 로컬로 넘어가지 않고 주소 없이 기다린다.
- Jetson USB-C(장치 모드)를 PC에 꽂자 `UsbNcm` · `RNDIS` 어댑터가 생기고 PC가 `192.168.55.100`을 받아 `192.168.55.1`이
  응답했다.
- PC에 `~/.ssh/id_ed25519`(암호 없음)를 만들고, 사용자가 비밀번호를 쳐서 Jetson `authorized_keys`에 올렸다.
- Jetson 유선 `enP8p1s0`("Wired connection 1")은 `connecting (getting IP configuration)`에 멈춰 있었다. 연결 설정을
  바꾸려면 sudo 비밀번호가 필요해서 사용자가 직접 실행했다.

  ```bash
  sudo nmcli con mod 'Wired connection 1' ipv4.method manual ipv4.addresses 192.168.127.2/24 ipv4.never-default yes
  sudo nmcli con up 'Wired connection 1'
  ```

- PC 이더넷은 다시 고정 `192.168.127.1/24`(게이트웨이 · DNS 없음).

### 결정

- 직결 유선은 양쪽 고정 IP — PC `192.168.127.1`, Jetson `192.168.127.2`, /24, 게이트웨이 없음. Jetson 인터넷은 지금처럼
  Wi-Fi로 나간다(`never-default`). 직결에는 DHCP 서버가 없어서 자동에 맡기면 Jetson이 주소 없이 남는다.

### 확인한 것

| 항목 | 값 |
| --- | --- |
| Jetson | 호스트 `mokpo`, 계정 `dongki`, L4T R36.4.7 (JetPack 6.2) |
| 유선 | `enP8p1s0` 1000 Mb/s, `192.168.127.2/24`, connected |
| PC → Jetson | 핑 0 ~ 1 ms, `ssh dongki@192.168.127.2` 키로 접속 |
| USB 장치 모드 | Jetson `192.168.55.1` (`l4tbr0`), PC `192.168.55.100` (DHCP) |
| Jetson Wi-Fi | `wlP1p1s0` → `CE312`, `192.168.1.82`, 기본 경로 |

- 문서는 Jetson을 "dongki"로 부르는데 실제 호스트 이름은 `mokpo`이고 `dongki`는 계정이다(`software/README.md`,

## 2026-10-14 (수) · 상위 제어: 무선 게임패드로 실차 조종 — Jetson 수신기, L1 데드맨

> 시간: 15:25 ~ 16:55 · 장소: PC, Jetson "mokpo" (계정 `dongki`, 유선 직결 `192.168.127.2`) · 날짜 근거: 세션 · 관련 이슈: N1 · N2 · R5 · R7

ESP32 핫스팟 웹 조종 (폰) 이 자주 끊기고 조작도 불편해서, PS3 모양 2.4 GHz 무선 패드의 수신기를 Jetson 에 꽂아 패드로 바로
모는 `pad.py` 를 만들었다 ([experiments/2026-10-13_vlm-drive](../../experiments/2026-10-13_vlm-drive/README.md)).
바퀴를 띄우고 실물 ESP32 로 앞 · 뒤 · 느린 속도 · 조향, 손을 떼면 바로 서는 것까지 됐다. 이어서 남는 버튼에 비상정지 (B) ·
한 단계 빠르게 (R1) · 제자리 90° (십자 좌우) · 주행 기록 (A) 을 붙였다. 패드 전원이 꺼질 때의 동작은 아직 보지 않았다.

### 한 일

> 혹시 지금 연결된 jetson 장치에 무선 컨트롤러를 연결해서 이걸 통해서 차량을 조작할 수 있게 만들 수 있을까?

> 지금eps32 핫스팟을 통한 웹 컨트롤러 방식을 쓰니까 끊기기도 잘 끊기고 조작도 불편하기도 하고 그래서 말이야 이걸 쓰면 개선이 되려나?

- 웹 경로와 비교: 지금은 폰 Wi-Fi ↔ ESP32 AP 가 무선 구간이고, 웹 쪽에는 늦게 도착한 명령이 바퀴를 다시 돌리는 문제
  (R1 · R2 · U3), 정지를 다시 보내지 않는 문제 (R4), 손 떼면 램프로 감속하는 문제 (R5) 가 열려 있다. 패드는 무선 구간이 패드 ↔
  전용 수신기뿐이고 그 뒤는 USB 시리얼 선 + 하트비트 워치독이라 이 문제들을 비켜 간다. 대신 수신기 거리 (싸구려는 5 ~ 10 m)
  와 Jetson 이 켜져 있어야 한다는 조건이 붙는다.
- 패드: DragonRise `0079:181c` "Controller" (안드로이드 배치). 게임패드 장치 `event6` 하나에 버튼 15 개가 이름대로 나온다
  (L1 = TL 310 · R1 = TR 311 · SELECT 314 · START 315). 스틱은 X · Y (왼쪽) · Z · RZ (오른쪽) 0 ~ 255, L2 · R2 는 버튼과
  아날로그 (BRAKE · GAS) 가 같이 나오고, 십자는 HAT0X · HAT0Y. 미디어 키용 장치 2 개 (System · Consumer Control) 가 따로
  생긴다. 바탕화면에 `dongki` 가 로그인돼 있어 udev uaccess 로 `event6` 을 sudo 없이 읽는다 (`input` 그룹은 아님).
- `pad.py`: evdev 를 표준 라이브러리 (ioctl · struct) 로 직접 읽는다. `show` (이벤트 그대로) · `learn` (안내대로 눌러 `pad.json`)
  · `drive`. `pad_ctl.sh` 로 뒤로 띄운다. 자체 시험에 가짜 패드 항목 12 개를 넣어 PC 에서 통과 (잡기 전 · L1 한 번 떼기 · 단계 ·
  손 떼면 `x` · 루프가 멈추면 host watchdog · SELECT · 수신기 빠짐).
- `learn` 을 앱 터미널로 돌렸는데 안내 순서와 다른 입력이 섞였다 (L1 자리에 R2, START 자리에 오른쪽 스틱). `show` 로 하나씩
  눌러 보며 배치를 확인해 `pad.json` 을 직접 썼다. `learn` 은 버튼 단계에서 스틱 축을 받지 않게 고쳤다.

> 근데 어차피 바퀴는 공중에 띄어나서 그냥 바로 해도 되는데 말이야

- 가짜 ESP32 단계를 건너뛰고 실물로 `pad.py drive` (바퀴 띄움). 메인보드가 꺼져 있어 (0.0 V) 켜자 "telemetry back".
  START → 워치독 켬, L1 + 왼쪽 스틱으로 앞 +150 · 뒤 −150, 살짝 밀어 +50 ~ +70 으로 천천히. 오른쪽 스틱으로 서서 · 가면서
  t ±400. 스틱이나 L1 을 놓을 때마다 `STOP (user)`.

> 안쓰는 버튼들은 뭐가 있지?

- R1 · L2 · R2 (아날로그 값도) · A · B · X · Y · 십자 좌우 · 왼쪽 스틱 좌우 · 오른쪽 스틱 위아래 · L3 · R3. MODE 는 기록에 안
  나왔다 (패드 안에서 아날로그 전환에 쓰는 듯).

> B: 비상정지 / R1 누르는 동안: 한 단계 빠르게 / 십자 좌우: 오도메트리로 제자리 90° 돌기 / A: 주행 기록 시작 / 끝 — 이건 다해주라

- B: 잡았으면 `x` 하고 놓기 (`w 0`), 잡지 않았어도 `x`. 다시 몰려면 START, 그 뒤 L1 을 한 번 떼야 움직인다.
- R1: 누르는 동안 속도 단계 하나 위 (150 → 200).
- 십자 좌우: L1 을 누른 채 스틱을 놓고 누르면 오도메트리로 제자리 90°. `motion.turn_by` 는 끝날 때까지 붙잡고 있어 패드를
  못 읽으므로, 같은 규칙 (`turn_cmd` 500 → 20° 안쪽 `turn_cmd_slow` 300, 허용 4°, 시간 2 s + 90° / `turn_min_dps`) 을 틱마다
  한 번씩 하는 상태로 짰다. 도는 중에 L1 을 떼거나 스틱을 건드리면 멈춘다.
- A: `record.py` 는 포트를 스스로 열어서 패드 프로그램과 따로 띄우면 한 포트를 둘이 나눠 읽게 된다 (보고 줄이 깨진다).
  `Recorder` 에 `link` 인자를 더해 패드 프로그램 안에서 같은 링크로 돌리게 했다. 처음 누를 때 Xtion · 웹캠을 뒤에서 열고
  (몇 초), 결과는 `data/logs/hallway-run/<시각>/`, 20 분 뒤 스스로 끝. 프로그램을 끝낼 때 녹화 파일을 닫고 `os._exit`
  (OpenNI 정리 중 멈춤을 피하는 `record.py` 와 같은 방식).
- 자체 시험에 9 항목을 더해 (R1 · B 두 개 · 왼쪽 90° · 오른쪽 시작 · L1 로 끊기 · 스틱으로 넘겨받기 · A) PC · Jetson 모두 통과.
  가짜 ESP32 를 데드밴드 100 으로 만들면 제자리 회전이 초당 11° 라 90° 가 시간 초과로 75° 에서 멈춰, 항목 5 와 같은 200 으로 맞췄다.

> 그래 이더넷 뽑고 지금 전원선도 잠깐 뽑았다 연결할거라서 켜지면 바로 저거 컨트롤러 대기 하고 있게 해야해

- 실물에서 R1 (`단계 200 (R1)`) · B 비상정지 · A 녹화가 동작했다 (녹화 51 s, Xtion · 깊이 · 웹캠 257 장씩 + 바퀴 기록).

- 등록하다 SSH 명령 안의 `pkill -f "python3 -u pad.py"` 가 그 SSH 셸 자신과 맞아 셸이 같이 꺼졌다 (같은 날 아침 bench.py 와

### 결정

- 조작: START 잡기 (`x` · `m 300` · `w 1`) · L1 누르는 동안만 움직임 · 왼쪽 스틱 속도 · 오른쪽 스틱 조향 · 십자 위 / 아래 속도
  단계 (100 ~ 300, 처음 150) · SELECT 놓기 (`w 0` — 폰 웹 조종으로 돌아갈 수 있게, N2).
- 스틱을 놓거나 L1 을 떼면 램프 없이 `x` (R5 에서 웹에 바라던 동작). 가속은 펌웨어 램프 그대로.
- 가면서 조향은 안쪽 바퀴를 0 · 거꾸로까지 줄인다 — 안쪽 바퀴를 앞으로 약하게 주는 것으로는 네 바퀴 스키드 스티어가
  돌지 않는다 (위 실측).
- 스틱을 살짝 밀면 펌웨어가 0 으로 치는 50 부터 시작한다 — 그대로 비례시키면 단계 150 에서 스틱 1/3 까지 안 움직인다.
- `open_serial` 이 리눅스에서 포트를 잠근다 (pyserial `exclusive`) — `bench.py` · `pad.py` · `drive.py` 가 한 포트에 같이 쓰지 않게.
- 폰 웹 조종과 같이 쓰지 않는다 (웹 버튼을 누르는 동안은 시리얼 `x` 가 덮인다, R7).

### 발견한 문제

- 잡을 때 첫 줄 (`x`) 이 "? unknown" 으로 버려졌다 — 포트를 열 때 생긴 출력 가능한 잡음이 앞에 붙은 것 (N1 대로 무시만 됨).
  `arm()` 이 `x` 를 먼저 보내므로 뒤의 `m` · `w 1` 은 들어간다.
- 자체 시험 5 (왼쪽 90° 돌기) 가 실패한다 — 작업 트리의 `robot.json` 보정값 (`track_eff_m` 0.79 → 0.92, 커밋 전) 과 가짜
  ESP32 의 '진짜' 윤거가 어긋나서다. 패드 작업과는 관계없다.

### 남은 일

- 새 조향 방식을 바닥에서 — 스틱 반 · 끝에서 실제로 도는지, 너무 급하지 않은지
- 실물로 십자 좌우 90° 확인. 90° 는 바닥에서 실제 각도를 재 봐야 한다 (스키드 스티어는 돌 때 미끄러져
  오도메트리보다 덜 돈다 — `track_eff_m` 보정)
- 조향이 실제로 맞는 쪽으로 도는지 (눈으로), 그리고 패드 전원을 끄거나 범위를 벗어날 때 L1 '뗌' 이 오는지 — 안 오면 마지막 상태가 남으므로
  대책이 필요하다

### 한 일

> 카메라 사진 만으로 위치를 잡는 실험이 필요하다고 했잖아 그걸 어차피 pc 가 아닌 jetson 에서 해야할 거니까 jetson 에 세팅해두고 해보면 안되나?
