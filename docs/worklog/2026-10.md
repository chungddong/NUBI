## 2026-10-13 (화) · 바퀴 제어: ESP32 바퀴 모드 — 보드 · 탱크 모드를 없애고 믹싱을 ESP32로, N1 수정

> 시간: 16:10 ~ 16:30 · 장소: PC (`F:\Develop\NUBI`) · 날짜 근거: 세션 · 관련 이슈: N1, H2, H3, N4 · 결정: [ADR 0001](../decisions/0001-wheel-board-pairing.md)

모터 보드 마스터를 믹싱 없이 바퀴별 값을 그대로 구동하는 빌드(passthrough)로 바꾸기로 하고([ADR 0001](../decisions/0001-wheel-board-pairing.md),
메인보드 펌웨어 자체는 저장소 밖에서 관리), 그에 맞춰 ESP32 펌웨어를 바꿨다. 프레임 `iSteer`의 의미가 바뀌므로 메인보드보다 먼저 해야 하는
단계다. 빌드와 오프라인 검증까지 했고, 보드에는 올리지 않았다.

### 한 일

#### `src/main.cpp`: 바퀴 모드 하나로

- 보드 모드(`v 0`), 탱크 모드(`v 1`), `v` 명령, 링크 B 반전(`invb`), `STEER_SIGN`을 없앴다. 남은 것은 한 가지다.
  `left = speed + turn`, `right = speed − turn`(`turn = steer × max / 1000`)을 계산해서, 두 링크에 같은
  (`iSpeed` = 왼쪽 = 마스터 바퀴, `iSteer` = 오른쪽 = 슬레이브 바퀴)를 보낸다.
- `i <0|1>`를 "좌우 바꿈"으로 바꿨다(NVS 키 `swap`). 마스터가 실제로 오른쪽 바퀴면 `i 1`로 명령과 텔레메트리를 같이
  맞춘다(H3). 옛 NVS 키 `mode` · `invb`는 지우지 않고 읽지도 않는다. `Preferences::remove()`는 키가 없으면 부팅마다
  오류 로그를 남기기 때문이다.
- 데드맨: 링크 A(앞축)는 필수, 링크 B(뒤축)는 첫 프레임 뒤에 합류하게 했다(옛 보드 모드와 같다). 축 하나에 좌우가 다
  있어서 앞축만으로도 직진하므로, 앞 마스터만 먼저 굽는 시험 순서와 맞는다. 탱크 모드처럼 "둘 다 필수"일 이유가 없다.
- 리포트 끝 `out A B` → `out L R`, `/api/status`의 `outA/outB/mode/invb` → `outL/outR/swap`.

#### N1: 콘솔 입력

- 출력할 수 없는 바이트(0x20 미만, 0x7E 초과)는 줄에 넣지 않고 호스트 워치독도 갱신하지 않는다. 넘친 줄은 잘라서
  실행하지 않고 통째로 버린다. 숫자만 보내는 속도 단축 명령(`atoi`)은 없앴다.
- `Still()`: 시리얼과 웹 모두 `|s|` · `|t|` < 50이면 0으로 처리한다(메인보드 `STAND_STILL_THRESHOLD`와 같은 규칙).
  조향도 넣은 이유: 바퀴 모드에서 `t 20`이 데드밴드를 거치면 ±20 %로 제자리 회전한다.
- 저장소 도구(hoverctl · speedsweep · test_stop · ledtest)와 RDK · Jetson 래퍼는 모두 글자로 시작하는 명령만 쓴다
  (일지 09-17 · 09-18 확인). 단축 명령을 없애도 영향이 없다.

#### 웹 페이지

- 구동 선택 · B 반전 · 조향 반전 칸을 빼고 "좌우 바꿈"(펌웨어 NVS)을 넣었다. 속도 반전은 브라우저 설정으로 남겼다.
- 텔레메트리를 ①좌/①우/②좌/②우 → 앞좌/앞우/뒤좌/뒤우로 바꿨다. 좌우 바꿈을 켜면 L/R이 바뀌어 보인다.

#### 문서

- wheel-controller README(Drive modes → Wheel mixing, 명령 표, Safety, Split boards), `system-overview.md`(계층 표,
  명령 표, 프레임 표, "구동 방식", 알려진 문제, 정해야 할 것), `firmware/README.md`, ISSUES(N1, 다음 할 일)
- 여러 계층에 걸친 결정이라 [ADR 0001](../decisions/0001-wheel-board-pairing.md)로 남겼다. "결정을 기다리는 것"에서
  보드 짝짓기를 뺐다.

### 확인한 것

- 빌드: RAM 14.0 %, Flash 61.5 %(805,909 B). 경고 없음.
- 파이썬 모델(ESP32의 `Still` · `Ramp` · `Deadband` · 믹싱 → passthrough `Pilot()` → `SendSlave(-pwmSlave)`)로 확인했다.
  - 클램프 200/400/700/1000 × 데드밴드 0/200 × 명령 격자(50 간격): 실패 0. 어느 모터 입력도 클램프를 넘지 않고,
    바퀴 진행 방향과 크기가 의도한 좌우 값과 같다.
  - max 400, 데드밴드 200 기준:

    | 명령 | 왼쪽 | 오른쪽 |
    | --- | --- | --- |
    | `s 300` | +350 | +350 |
    | `t 1000` | +400 | −400 |
    | `s 300` + `t 500` | +400 | +250 |
    | `i 1`일 때 `t 1000` | +400 | −400 (프레임만 뒤바뀜) |
  - 정지에서 출발: 첫 틱 210, 이후 틱마다 +10. 데드밴드 점프가 그대로다.
  - N1: `\x00\xff1⏎` · `s 1` · `s 49` → 0, `\x00\x80s 120⏎` → 120(잡음을 걸러 내도 명령은 산다).
  - `(x, x)`는 옛 보드 모드의 "속도 x, 조향 0"과 모터 입력이 같다(마스터 −x, 슬레이브 +x).
- 웹 페이지 스크립트를 node에서 DOM 대역으로 돌렸다. 전진 50 % → `s=200&t=0`, 우 75 % → `s=0&t=750`, 좌우 바꿈 →
  `/api/cfg?swap=1`, 바꾼 뒤 텔레메트리 좌우가 뒤바뀌어 표시된다. 옛 `mode=` · `invb=` 요청은 나가지 않는다. PASS.
  브라우저 창은 로컬 파일 스크립트를 못 돌려서 화면 렌더링은 확인하지 못했다.
- `tools/test_stop.py` PASS.

- `main.cpp`가 그 헤더에서 쓰던 것은 설정 · 보내기 · 받기 함수, 구조체 2개, `CLAMP` 매크로뿐이었다. 이름을 `HoverBegin` ·
  `HoverSend` · `HoverReceive` · `HoverCommand` · `HoverFeedback`으로 바꿨고, 보내기 함수의 인자 순서(조향 칸 먼저)는
  그대로 두었다.
- 받기는 버퍼에 한 프레임(22 B) 이상 있을 때만 읽고, 시작 바이트(0xCD 0xAB)를 찾아 CRC가 맞는 프레임만 넘긴다. CRC가
  틀린 프레임 뒤에도 같은 호출 안에서 계속 찾는 점이 예전과 다르다.
- GPL 원본 두 개는 저장소에서 빼고 로컬(`firmware/hoverboard-mainboard/local/upstream-examples/`)에 두었다.

### 결정

### 확인한 것

- 빌드: RAM 14.0 %, Flash 61.5 %(805,697 B, 예전 헤더 때보다 212 B 작음). 프레임 크기 9 / 22 B, 필드 위치, CRC 검사값
  0x31C3(파이썬 `binascii.crc_hqx`로 같은 값 확인)을 `static_assert`로 컴파일 때 확인했다.
- GPL 헤더를 `include/`에서 치운 상태로 빌드된다. 다른 코드가 그 헤더에 기대지 않는다.
- 이력: 지운 경로가 24개 커밋의 어느 트리에도 없고, 바꾼 문자열도 0건이다. 최신 트리 해시가 정리 전과 같다.
  로컬 전용 파일(메인보드 폴더, Wi-Fi 설정, 휠 모터 STEP 등)은 그대로다. 저장소 65.5 MB.
- 외부 라이브러리 파일이나 라이선스 문구는 없다. 시뮬레이터의 three.js · three-mesh-bvh(MIT)는 실행할 때 CDN에서만
  불러온다.
